HackerTube
It was Friday night at 11pm, I was tired, I went to YouTube to watch something and realized that I was looking at an enshittified wall of slop. Insanely exaggerated thumbnails, dumb recommendations of the same tired topics, truly terrible idiocracy-grade content. I'm sure this algorithm works well for the median person on the internet, but it definitely does not work for me. So this morning (Saturday) I took a hold of my Opus 5.5 and gave it the task: Let's write our own YouTube clone based on whatever videos have been recommended on Hacker News. And Opus came back with: hackertube.org!
Opus downloaded all comments of HackerNews, filtered them, ran Sonnet over them in a Workflow (Claude Code feature), got rid of spam, and narrowed everything down to 40K comments recommending a YouTube video. In total, we get 6,454 YouTube videos that have been recommended by a few people on HN from 2007-2026 across 150 topics. Then we wrap it up in a YouTube UI, get a domain, push to a VPS, secure, harden, optimize and voila!
HackerTube:
- Contains quality content
- Uses the 50% thumbnail instead of the uploaded thumbnail
- Custom and good ForYou recommendations without any user accounts, storing state in local browser session
- Keyboard shortcuts
- Export of the site's data available to give to your agent to easily create your own version
This takes ~2 hours now. I can breathe again. Thank you Opus 5.5 <3.
EDIT: A little bit more on my process. I use Claude Code (desktop app for Mac). I use Opus 5.5 on Medium effort as my default. I don't actually do anything resembling traditional engineering anymore (read/write code, run commands in a terminal, or etc.), I only talk to Claude and have it do everything. In this case, the only "manual work" I did was: 1) I had to create some kind of API key from Google Cloud UI to query YouTube for video metadata, 2) I booted up a VPS box and 3) I bought the domain name. I worked on this in between Claude's actual work so it still feels a little bit like team work :) Once the box was up I gave Claude the IP and told it update, deploy, secure, harden and optimize the code, and it did the whole thing.

The TUI uses 24-bit color when the terminal advertises it with COLORTERM=truecolor, and the
nearest 256 colors otherwise (macOS Terminal.app, or most terminals over ssh, which does not
forward COLORTERM). If your terminal supports 24-bit color but does not advertise it, run

For reviewing changes in a browser, see codereview.
Note: codereview is at v0.0.0; use it at your own risk.
omnidiff --headless BEFORE AFTER, or its synonym --batch, prints the diff as plain text, with
optional color, instead of opening the TUI. Use this for scripts or CI. Headless mode also starts
automatically whenever stdout is not a terminal, for example when piped into less or redirected to
a file. Because of this, omnidiff BEFORE AFTER | less works without the flag.
OmniDiff collapses long runs of unchanged lines. It keeps 3 lines of context on each side of a
change (override with --context N), the same convention as diff -u. OmniDiff also prefixes each
hunk with the nearest enclosing function, class, or struct line, when that line is not otherwise
visible. This shows the location of a change deep inside a large file.
Colors are on by default; pass --color never, or set NO_COLOR=1, to disable ANSI colors, for
example when you redirect output to a file - --color always forces them even under NO_COLOR.
OmniDiff exits 0 on success and 2 on error. For scripting, pass --exit-code to additionally
get 1 when the files differ. This follows the diff(1) convention. --exit-code is opt-in rather
than the default for the same reason git diff exits 0 even when files differ: OmniDiff's usual
non-interactive callers are version control systems driving it as a display tool, and they read a
non-zero exit as "the tool failed" - jj warns on every file, and git difftool with
difftool.trustExitCode=true aborts the whole diff. (The 7-argument GIT_EXTERNAL_DIFF form stays
at 0 even with --exit-code, since git treats a non-zero exit there as fatal.)
omnidiff --mode json BEFORE AFTER prints the diff as one JSON object. Its fields are described
in src/tui/json_output.schema.json, a JSON Schema.
OmniDiff is a git difftool backend. Run the interactive setup wizard, which asks
whether to configure it globally or for the current repository only:
omnidiff git configure
git config difftool.omnidiff.cmd 'omnidiff "$LOCAL" "$REMOTE"'
git difftool --tool=omnidiff
Run git config diff.tool omnidiff to make plain git difftool use OmniDiff by default, without
needing --tool. If you do not want git to ask "view diff ... [Y/n]?" before every file, run git config difftool.prompt false.
git difftool opens the interactive TUI. git diff and git log -p never do. git diff
pipes its output through git's pager, and a full-screen TUI cannot draw onto a pipe, so OmniDiff
always falls back to plain text there regardless of terminal or GIT_EXTERNAL_DIFF config (see
"Headless / batch mode" above). If you want the interactive viewer from git, use git difftool,
not git diff. If git difftool still doesn't open interactively over SSH, reconnect with
ssh -t — the session needs an allocated pseudo-terminal; tmux panes always have one.
OmniDiff also works directly with git diff and git log -p, through GIT_EXTERNAL_DIFF. This
path needs no difftool config:
GIT_EXTERNAL_DIFF=omnidiff git diff
Pictures, archives, fonts and the rest of the supported content get a short
report of what changed in them. Any other binary file gets a one-line Binary file <path> differs
notice instead of a diff, the same stand-in git and diff(1) print for them. Neither ever blocks
the rest of a git diff: an external diff that exits non-zero makes git abandon the entire run,
so OmniDiff reports an unshowable file as a successful diff of nothing rather than as a failure.
jj does not read git's difftool/diff.external settings, even in a colocated repo, so it needs
its own configuration. Run the setup wizard:
omnidiff jj configure
jj config set --user merge-tools.omnidiff.program omnidiff
jj config set --user merge-tools.omnidiff.diff-args '["$left","$right"]'
jj config set --user merge-tools.omnidiff.diff-invocation-mode file-by-file
That registers jj diff --tool omnidiff. To make it the default for plain jj diff as well:
jj config set --user ui.diff-formatter omnidiff
Use --repo in place of --user to configure the current repository only.
diff-invocation-mode = "file-by-file" is required. jj's default hands a diff tool two
directory trees; OmniDiff diffs two files, so without this setting every invocation fails. With
it, jj passes one changed file pair at a time, keeping each file's real path and extension, so
language detection works exactly as it does under git.
jj diff runs its formatter under a pager, so OmniDiff renders in its non-interactive text mode
there - the same output git diff gets. jj has no equivalent of git difftool's interactive
per-file viewer (its terminal-attached hook, ui.diff-editor, is for jj diffedit/jj split,
which edit the right-hand side and read it back - not something a read-only viewer should claim to
do), so for the full-screen TUI on a jj repo, run omnidiff BEFORE AFTER directly.

10. Nibnib: Image compression with extreme decompression speed
FULL TEXT
88 points · 11 comments · raphlinus

Article
An image format tuned for extreme decompression speed.
This image format originated as an experiment to see what image quality and performance were possible for DVI output on an RP2350 microcontroller. On devices of that class, it's common to use low bit depth images and palette lookup. There's a budget of approximately 6 cycles per pixel, and that's enough for a pixel fetch, palette lookup, and store into the line buffer, but not a lot of room to spare.
The nibnib format uses a palette at its core, but surpasses palette images in quality because the palette stores a delta rather than the absolute color, vastly improving soft regions. It achieves its extreme speed by decoding two pixels at a time, from a single byte of input, thus attaining 4bpp compression.
The decompression process is simple and deterministic. There are many choices when encoding; the algorithm is asymmetric in that regard.
Decoding works in pixel pairs. The last decoded pixel is doubled up. Then we read a byte from the input stream, and look it up in the palette. That 32-bit value is added to the doubled-up previous pixel, yielding two 16bpp (RGB 565 format) pixels. The low 16 bits are the left pixel. That's it.
Here's the inner loop (lightly adapted from the Rust source):
// first two pixels copied from src[0..4], initializing pix
for x in 1..(width / 2) {
let inp = src[x + 3];
pix = ((pix >> 16) * 0x10001).wrapping_add(pal[inp as usize]);
out[x * 2] = pix & 0xffff;
out[x * 2 + 1] = pix >> 16;
}
The RP2350 on-the-fly decoder implementation is included in the image demo of the vic-2350 repo.
As with many image compression formats, nibnib is defined by the decoding process, which is deterministic and straightforward. Encoding is fundamentally a search through the space of possible encoded images to find one that decodes to a (hopefully) high quality replica of the original. In nibnib, this search is quite asymmetrical; the current encoder is orders of magnitude slower than decoding. By contrast, in JPEG, the DCT transform is invertible by its mathematical nature, and quantization is also easy; at baseline, encoding and decoding are about the same speed, though search can be used to fine-tune parameters and micro-optimize quality.
Nibnib has two main dimensions for the search: choice of palette, and selection of codewords. For the initial version, the palette has a cube of small delta values plus a block of random values, chosen by weighted Gaussians. The cube is necessary to ensure that values near 0 and full scale can be attained without risk of overflow; without the cube entries, you get bad artifacts. First is the original image, then the image encoded with a random-only palette, finally with both the cube and random values.
The random Gaussian process was refined on an ad-hoc basis, using guesses about reasonable values. In particular, the delta between the two pixels gives a tradeoff between sharpness and noise; keeping it small makes the image smoother at the cost of reduced ability to encode sharp edges.
In the current encoder, the palette is not chosen adaptively based on the input image, but that is most definitely an opportunity to improve quality.
The basic encoding loop is conceptually straightforward, but the details are a bit subtle.
Conceptually, it simply tries all 256 palette entries, and chooses the one with the minimum error. Then it takes that error and distributes it using Floyd-Steinberg weights. Subsequent pixels fit not the source pixel value, but the source pixel plus errors from previous iterations, weighted.
The loop as described above is quite similar to error diffusion with a quantized palette, a very popular technique. However, that's usually done with one pixel at a time, while the nibnib algorithm generates two pixels at a time. The palette entry is chosen to minimize the error of both pixels, giving somewhat higher weight to the sum rather than the difference, modeling the fact that the human visual system is more sensitive to lower spatial frequencies.
What's presented is a basic, working image compression technique. Quality can be improved significantly by tuning both major aspects of the search: coming up with an optimized palette, and also a deeper search for error-minimizing pixels. For this pixel, two choices might have roughly equal error, but one might make the search for the next to be considerably more favorable.
Currently, the artifacts trail to the right of sharp edges, but that's a consequence of the greedy search. It's not hard to see how to make encoding work right to left (or even boustrophedonically, alternating direction each row) while decoding is still left to right, as the addition step is invertible in practice (there's a bit of subtlety around the interaction of the carry and the pixel duplication).
Both improvements would slow the encoder down considerably, though decoding speed would be unchanged. Another direction is to make the encoder faster. For example, brute force search through palette entries can almost certainly be improved, perhaps in combination with making the palette more structured. All these improvements can be made with the existing decoder.
The image format is extremely unsophisticated: 2 bytes each for width and height, then 256 32-bit palette entries, then the rows in order.
Each row begins with two pixels (RGB 565 each), followed by ((width - 2) / 2) bytes, each indexing the palette. The row stride is rounded up to a multiple of 4 bytes.
Currently there's no other metadata; the format is not intended for archival, and is much more likely to be used when integrated tightly with the decoder.
