Wiz Research, Ikotas Labs, Metnir, Rapid7, and Xint independently uncovered two critical remote code execution vulnerabilities in NGINX, software used to receive and route traffic to production applications and APIs.
Successful exploitation could let attackers take control of affected NGINX servers, steal sensitive data, tamper with websites, or disrupt services.

Overview
Wiz Research, Ikotas Labs, Metnir, Rapid7, and Xint independently uncovered CVE-2026-123633 and CVE-2026-123007, two critical unauthenticated remote code execution vulnerabilities in NGINX, and reported them to F5, the company behind NGINX. Successful exploitation can compromise the server running NGINX, allowing attackers to execute code, steal sensitive data, tamper with websites, or disrupt services.
NGINX often handles traffic for several applications, so a single affected deployment can put multiple services at risk. The flaws are in NGINX itself and can affect websites even when their own application code is secure. Both vulnerabilities require HTTP/2 to be enabled on the affected NGINX server. Our testing of CVE-2026-123007 demonstrated code execution on NGINX serving ordinary static files, without a backend application or third-party modules.
Wiz Research used Wiz Atlas, the harness powering Wiz’s AI Code scanning solution, to discover both vulnerabilities. Our researchers used Gemini 4 Carbon and ChatGPT 5.6 Sol to validate the impact of both vulnerabilities, confirming that each could allow an unauthenticated attacker to execute code on the server. We reported our findings to F5 and worked with its security team on remediation and coordinated disclosure.
The integer underflow vulnerability dates back to NGINX 1.9.5 in 2015, meaning it had been hiding in the code for more than a decade. The use-after-free vulnerability had been there for nearly six years. Like the PHP2Shell vulnerabilities we reported last month and Java4Shell, disclosed yesterday by Calif, these are memory-safety flaws that have historically been extremely difficult to discover and exploit. Finding them often requires tracing subtle interactions between memory operations and multiple code paths. For years, that complexity itself created a practical barrier. AI is fundamentally dissolving that barrier. As AI models get better at following those interactions, both researchers and attackers can uncover longstanding flaws in software that powers the internet and modern applications. The fact that multiple independent research teams uncovered the same vulnerabilities in both PHP and NGINX, after they had remained in the code for years, makes this shift particularly striking. And as AI capabilities advance, each new generation of models may uncover even more complex vulnerabilities that were previously beyond practical reach. Complexity can no longer be relied upon as a barrier to discovery or exploitation. This changes not only which vulnerabilities can be found, but how quickly longstanding risks can become real threats.
Over time, finding and fixing these flaws can harden the software we all depend on. In the near term, faster discovery and a shorter window between disclosure and exploitation add to an already demanding workload for security teams. Turning a published fix into protection in production still takes substantial manual work, from validating patches to coordinating rollouts with service owners. We recommend focusing on how quickly you can reduce exposure in production. Identify deployments running the affected version and configuration, prioritize those an attacker can reach, and apply mitigations while patches are tested and rolled out.
In this post, we explain the vulnerabilities and their impact, and provide mitigation and detection guidance. Organizations should identify affected deployments and apply the security updates as soon as they are available. If upgrading is not immediately possible, temporarily disable HTTP/2.
NGINX can also serve web content directly and act as a load balancer, distributing traffic across multiple servers. A single NGINX deployment can serve several applications, making it a shared entry point for the websites and APIs behind it.
The Vulnerabilities
Both vulnerabilities are memory-safety issues in how NGINX handles HTTP/2 traffic. In CVE-2026-123633, a connection's memory is freed while a request still needs it, creating a use-after-free. In CVE-2026-123007, incorrect flow-control accounting leads to an invalid memory copy. Each can lead to unauthenticated remote code execution on the NGINX server.

Technical deep dive
CVE-2026-123633: An active connection marked as reusable
NGINX keeps a list of connections that it can close when it needs room for new ones. An HTTP/2 connection can join this list when it has no active requests, but must leave it when a request starts.
We start by sending only part of a HEADERS frame, which carries an HTTP/2 request's headers. With no active request streams,ngx_http_v2_handle_connection() marks the connection as reusable while waiting for the rest:
ngx_reusable_connection(c, 1);
if (h2c->state.incomplete) {
return;
}
When we send the rest of the frame,ngx_http_v2_create_stream() creates a request stream and increments h2c->processing. However, it does not remove the connection from the reusable list. We now have a request being processed on a connection that NGINX still considers safe to close.
Triggering the use-after-free
Next, we need NGINX to close this connection while the request is still running. Forwarding the request to an application server can trigger this.
Opening an upstream connection calls ngx_get_connection(). When free connection slots run low, ngx_drain_connections()selects reusable connections to close. Our HTTP/2 connection is still on that list, so NGINX can select it while processing its own request.
Before closing it, NGINX tries to send a GOAWAY frame to notify the client. Even creating this frame can fail, for example, if NGINX has reached its internal frame limit for the connection and has no frame available for reuse. In that case, the error path closes the connection and frees the memory associated with it. Processing then resumes in the original request, which still uses that memory. We have reached the use-after-free.
From use-after-free to remote code execution
The freed memory can now be reused for other data. The request-processing code still follows its old pointers, treating the new contents as the original request or connection.
This use-after-free can lead to unauthenticated remote code execution on the NGINX server.
HTTP/2 allows several requests, called streams, to share one connection. Flow control limits how much response data NGINX can send before the client is ready to receive more. NGINX tracks the connection's remaining allowance in a counter called h2c->send_window.
When NGINX queues response data, it subtracts that data's size from the counter before sending it. If a stream is canceled while its data is still queued, ngx_http_v2_filter_cleanup() removes the unsent data and returns the unused allowance:
h2c->send_window += window;
This refund does not check HTTP/2's maximum allowed window. If the client has already increased the allowance while data was waiting to be sent, the refund can push the counter above that maximum. NGINX is now tracking a value the rest of its HTTP/2 code assumes cannot occur.
A bounds check that no longer works
The next problem is in ngx_http_v2_state_window_update(), which checks whether an increase would exceed the limit:
if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window)
The check subtracts the current allowance from the maximum to calculate how much room remains. But the refund has already pushed the allowance past that maximum. Because the calculation uses an unsigned integer, which cannot represent a negative number, the subtraction wraps around and underflows to a very large positive value. The check now treats an invalid counter as though it has plenty of room left and allows further increases.
From an invalid length to remote code execution
The invalid counter eventually reaches ngx_http_v2_send_chain(), where it is converted to the signed integer type off_t to calculate how much data to send. A sufficiently large value becomes negative. That negative length then reaches the code that describes a portion of a response buffer, leaving its end pointer before its start pointer.
When the TLS send path in ngx_ssl_send_chain() processes this malformed buffer, further signed and unsigned conversions turn the invalid length into an out-of-bounds memory copy. An attacker can use this to disclose memory, corrupt the heap, and lead to unauthenticated remote code execution on the NGINX server.
We confirmed remote code execution with an ASLR bypass on official NGINX 1.31.7 and 1.31.8 builds. The tested path used HTTP/2 over TLS on 64-bit systems serving response data from memory. Ordinary static files can reach this path through standard TLS processing, without a backend application or third-party module.
Exploitation
To confirm these vulnerabilities, Wiz Research built proof-of-concept exploits and managed to run them in multiple lab settings against servers running common NGINX configurations we’ve seen in customer environments. In the interest of customer protection, we will not be releasing these exploits at this time.
Like other memory-safety issues, such vulnerabilities are difficult to exploit remotely and require the attacker to disclose memory addresses, groom and shape the heap correctly, and handle different NGINX versions, builds, and configurations. In reality, attackers may not need to target every single configuration, and we have seen in PHP2Shell that widespread attacks initially start against packaged products where many customers use the exact same build and configuration. Motivated attackers may tailor exploits for specific targets.
Any exploit assumes the attacker is able to communicate directly with the affected NGINX server. CDNs and WAFs that terminate HTTP/2 may mitigate parts of the exploit by not reflecting the exact payload back to the underlying NGINX server. This depends on implementation.
Specifically, CVE-2026-123007 requires the attacker to send a large number of WINDOW_UPDATE records to increase it to an arbitrary value. Detection rules covering long standing HTTP/2 connections sending large amounts of data may hint at an attack associated with this vulnerability. CVE-2026-123633 has different exploitation constraints and is more likely to be exploited when NGINX is configured in proxy configuration.

Conclusion
With NGINX handling traffic for critical websites and applications, the impact of flaws in its core extends far beyond a single service. This research is another example of AI uncovering critical vulnerabilities in widely deployed infrastructure. The flaws were already there; AI helped us find them.
As we saw with PHP2Shell, AI is changing the economics of vulnerability research. The same capabilities that help defenders uncover flaws can also help attackers investigate them. Software that has been used and reviewed for years still needs to be examined as these tools improve.
The opportunity is to make this work routine: finding vulnerabilities in the software organizations depend on and working with maintainers to fix them. Our collaboration with F5 brings that approach to NGINX, helping protect the applications and services behind it.

10. Lessons from Telegram's RCE
FULL TEXT
1 points · 0 comments · shcallaway

Article
On Nov. 10, Telegram CEO Pavel Durov announced that any Telegram message can now become an app. A day later, a message became remote code execution instead. Telegram patched it with a seccomp filter, and two days after that we bypassed the filter.
Two exploits in four days suggest the issue is architectural, and that it needs more than another patch. So this post does two things. It recaps what happened, and it shows how to run JavaScript inside a chat message properly, using the hardened design we built.
Summary
Running third-party code inside a messenger is the same problem browsers face, and their answers carry over:
- Assume the engine is already compromised, and design for what the attacker holds next.
- Run it outside the process that holds accounts, messages and keys.
- Confine it inside that process with SFI, one instance per widget.
- Treat everything it says as tainted until the host validates it.
- Make seccomp an allowlist, and remember it can’t fix the kernel behind the calls it allows.
With those layers in place, an engine bug should end as a crashed widget instead of a compromised account. The same list applies to any app that runs code arriving in a message, a document or a file.
Four Days, Two Exploits
| Date | What happened |
|---|---|
| Nov. 10 | Pavel Durov announces the feature: Any Telegram message can now become an app. |
| Nov. 11 | V12 posts a video showing that any Telegram message can turn into RCE. |
| Nov. 12 | Telegram adds a seccomp filter to address the problem and makes the feature allowlist-only. |
| Nov. 14 | We demonstrate that the seccomp filter can be bypassed. |
If you missed it: Widgets arrived with Bot API 10.4. A widget is a small HTML document that a bot sends inside a message, and Telegram runs its JavaScript on your device in QuickJS, a compact engine written in C.
The attacker is anyone who can register a bot. The input is a full programming language.
The Sandbox That Wasn’t
Telegram’s documentation describes the widget sandbox as a set of JavaScript-level rules: no network access, checked page changes, and caps on CPU and memory.
Those rules live in the engine’s own code. One use-after-free or out-of-bounds write in QuickJS, and the script is reading and writing process memory. The rules stop mattering.
That is how the first release fell. At launch the engine ran on a thread inside the Telegram app, so an engine bug ran with everything the app holds.
The Nov. 12 fix moved the engine into its own process and put a seccomp filter on it. That was a real step forward, and it still wasn’t enough:
- The seccomp rules are a denylist. The filter names roughly 30 calls, such as ptrace, bpf and mount. Everything else goes through, including every ioctl.
- One process serves every widget. The app manifest says so in a comment. A compromised widget from one bot shares an address space with every other bot’s widgets.
- Nothing confines QuickJS inside that process. The engine sits in one native library with the validator and the renderer. A bug in the engine is a bug in everything next to it.
Seccomp decides which calls are permitted. It can’t make the permitted implementations safe.
We reached code execution outside the seccomp filter in two independent ways. The first uses a widget vulnerability that seccomp does not cover to get RCE directly. The second chains two vulnerabilities, a widget vulnerability that seccomp does cover and a kernel vulnerability, to break through seccomp. Given how the current implementation works, both paths admit many variants that would yield further bugs, so we are holding the details for now.
The lesson for anyone shipping a script engine: Assume the engine is already compromised, and design for what the attacker holds next.
NebuSec Hardening for the Widget Runtime
Pointing out gaps is only useful if we can also show how to close them, so we built a hardened version of the widget runtime.
The goal is to strike a balance between flexibility, security and high performance. Our hardened widget runtime puts three boundaries around QuickJS:
- A dedicated process. Widget JavaScript runs in an Android isolated service and reaches Telegram only through explicit, validated instructions, with stricter seccomp rules on top.
- Software fault isolation. QuickJS is compiled with a constrained memory and execution model that confines memory corruption to a designated memory region.
- A tainted boundary. RLBox marks every value that leaves the engine as untrusted until the host validates it.
The rest of this post walks through each choice, starting with the one we didn’t make.
Why Not Just Use V8?
QuickJS was not designed to run untrusted code. The first option to consider is replacing it with a more battle-tested JavaScript engine, such as V8, SpiderMonkey or JavaScriptCore.
How many V8 engines are running on your device?
Had we made this decision before 2023, the only drawback might have been the size of these engines. Today, memory read/write primitives inside a complex JavaScript engine are within reach of a wide range of attackers, and a JIT compiler only adds more attack surface. We would be trading substantial storage overhead for little improvement in the isolation guarantees we actually need.
If attackers are ultimately destined to acquire arbitrary memory read and write primitives, why not embrace that inevitability and focus instead on fundamentally constraining the reach and capabilities of those primitives? Luckily, modern software development has set a clear path.
If It Looks Like a Duck and Quacks Like a Duck
Telegram widgets parse HTML, run JavaScript and respond to user interaction. This is the same combination a web browser handles.
To be clear, we’re not going to embed an entire browser into an IM application, although some companies have already done that. Instead, we’re borrowing a page from the browser’s architecture.
At launch, their biggest shortcoming lay in their approach to isolation: They relied on threads, which provide no memory isolation from the host application, since threads share the same address space.

The widget’s DOM layer records this modification and sends a batch of operations over a Unix domain socket from the isolated engine process. Telegram’s app process validates the batch and forwards accepted operations over a second IPC channel to an isolated LiteHTML renderer. Render output returns to the app, where the native graphics path redraws the widget. User interactions, dimensions and other events travel back through the engine socket to the JavaScript process.
Inside the trusted app process, the widget host coordinates those boundaries: one IPC client talks to the engine, a Rust validator checks every returned operation, a second client talks to the renderer, and Skia remains the final native drawing path.
So the application keeps its flexibility while QuickJS runs in a dedicated process. What’s more, that process can be further confined with stricter seccomp rules, which limit what attackers can do after gaining code execution in the widget process.
Inside that engine process, framed IPC reaches SandboxEngine, which can enter the per-widget QuickJS sandbox only through the RLBox bridge.
Stricter means an allowlist built from the calls the service actually makes, with arguments filtered too, ioctl included. A denylist only covers the kernel bugs someone has already thought of.
Le Pouvoir Arrête le Pouvoir
Power checks power, as Montesquieu put it. Process isolation and seccomp are necessary, but they are not silver bullets. A vulnerability in the kernel code behind an allowed syscall can remain reachable after an attacker compromises QuickJS. Seccomp decides which calls are permitted, but it can’t make the permitted implementations safe.
This is where software fault isolation, or SFI, enters the picture.
SFI is a way to run a potentially vulnerable component inside a restricted part of a process. The component still executes native machine code, but its memory accesses and indirect calls are constrained. It can’t treat an arbitrary number as a pointer into the rest of the process or as an address to jump to.
That distinction matters here. Android process isolation keeps the widget service separate from Telegram’s main process, and seccomp restricts the service’s syscalls. Neither prevents a memory corruption bug in QuickJS from taking control of other native code in the widget service. If that happened, the attacker could try to use syscalls that the service legitimately needs and seccomp therefore permits. SFI places another boundary around QuickJS itself.
We’d like to enforce the following rules:
- Memory access stays within a specific range of linear memory. We want to transform all absolute memory access into relative access by offset. Even if a corrupted QuickJS state produces an address outside the permitted memory, execution traps instead of accessing the service’s native heap.
- Indirect calls have constrained targets. Attackers love gaining arbitrary function calls by abusing indirect calls or dynamic binding mechanisms. One possible approach is turning function calls into function table indexing, where type checking can be applied.
WebAssembly offers precisely the execution semantics we require. Our implementation enforces that boundary by compiling the C version of QuickJS to WebAssembly, translating the WebAssembly to C with wasm2c, and compiling the generated C into the Android library.

SFI doesn’t make QuickJS correct. A memory bug still lets the script corrupt anything inside its own linear memory, and with it everything the engine reports to the host. What changes is where the damage stops.
Two bonuses come along. The generated code is portable C, so the same layer works on platforms where an app can’t easily spin up a locked-down helper process. The approach also has production precedent: Firefox has sandboxed libraries such as Hunspell and Ogg the same way since 2021.
Bridge the Gap
But as always, the devil is in the details. QuickJS doesn’t run a widget entirely on its own. It must receive scripts, return results and call a small set of host functions, and each exchange crosses the SFI boundary. In other words, we have to handle all of this cross-boundary traffic. RLBox is the framework we use to manage that boundary, making sandbox values visibly untrusted and giving the host checked ways to call QuickJS and copy data in and out.
RLBox provides an elegant solution to this problem by leveraging the C++ type system to enforce security constraints at compile time.
At its core lies a simple yet powerful abstraction: tainted<T>. Any value originating from the sandbox is treated as untrusted, and the host must explicitly validate it before using it in trusted operations. RLBox also mediates pointer conversions, memory transfers and callbacks across the sandbox boundary.
Two habits make the boundary stronger:
- Keep the list of host functions short. Each function the engine can call is a capability. A widget needs to emit page changes, set timers, read its state and post a request to the bot. It doesn’t need files, sockets or the host’s allocator.
- Give each widget its own sandbox instance. Every instance has its own linear memory, so a compromised widget from one bot can’t read another bot’s widget, even inside one process.
In short, WebAssembly constrains what QuickJS can access, while RLBox governs how QuickJS interacts with the outside world.
The renderer repeats the same containment pattern independently. Its IPC service enters a separate RLBox bridge, and LiteHTML parses and lays out the widget inside its own wasm2c sandbox.

This architecture, however, is by no means a guarantee of security. It merely isolates QuickJS and LiteHTML, while other code paths involved in rendering, such as Skia, remain outside the sandbox’s protection. In fact, we successfully exploited a vulnerability in Skia to achieve arbitrary code execution once again.
Conclusion
The broader lesson is not that applications can never run untrusted JavaScript; it is that the engine cannot also serve as the security boundary. Start from compromise: isolate the runtime from application secrets, confine each widget’s memory, keep host capabilities narrow and validate every value that crosses back. No layer is perfect, but together they can change the outcome of an engine exploit from application compromise to a contained widget failure.
