Successful exploitation could let attackers take control of affected NGINX servers, steal sensitive data, tamper with websites, or disrupt services.

Overview
Wiz Research, Ikotas Labs, Metnir, Rapid7, and Xint independently uncovered CVE-2026-123633 and CVE-2026-123007, two critical unauthenticated remote code execution vulnerabilities in NGINX, and reported them to F5, the company behind NGINX. Successful exploitation can compromise the server running NGINX, allowing attackers to execute code, steal sensitive data, tamper with websites, or disrupt services.
NGINX often handles traffic for several applications, so a single affected deployment can put multiple services at risk. The flaws are in NGINX itself and can affect websites even when their own application code is secure. Both vulnerabilities require HTTP/2 to be enabled on the affected NGINX server. Our testing of CVE-2026-123007 demonstrated code execution on NGINX serving ordinary static files, without a backend application or third-party modules.
Wiz Research used Wiz Atlas, the harness powering Wiz’s AI Code scanning solution, to discover both vulnerabilities. Our researchers used Gemini 4 Carbon and ChatGPT 5.6 Sol to validate the impact of both vulnerabilities, confirming that each could allow an unauthenticated attacker to execute code on the server. We reported our findings to F5 and worked with its security team on remediation and coordinated disclosure.
The integer underflow vulnerability dates back to NGINX 1.9.5 in 2015, meaning it had been hiding in the code for more than a decade. The use-after-free vulnerability had been there for nearly six years. Like the PHP2Shell vulnerabilities we reported last month and Java4Shell, disclosed yesterday by Calif, these are memory-safety flaws that have historically been extremely difficult to discover and exploit. Finding them often requires tracing subtle interactions between memory operations and multiple code paths. For years, that complexity itself created a practical barrier. AI is fundamentally dissolving that barrier. As AI models get better at following those interactions, both researchers and attackers can uncover longstanding flaws in software that powers the internet and modern applications. The fact that multiple independent research teams uncovered the same vulnerabilities in both PHP and NGINX, after they had remained in the code for years, makes this shift particularly striking. And as AI capabilities advance, each new generation of models may uncover even more complex vulnerabilities that were previously beyond practical reach. Complexity can no longer be relied upon as a barrier to discovery or exploitation. This changes not only which vulnerabilities can be found, but how quickly longstanding risks can become real threats.
Over time, finding and fixing these flaws can harden the software we all depend on. In the near term, faster discovery and a shorter window between disclosure and exploitation add to an already demanding workload for security teams. Turning a published fix into protection in production still takes substantial manual work, from validating patches to coordinating rollouts with service owners. We recommend focusing on how quickly you can reduce exposure in production. Identify deployments running the affected version and configuration, prioritize those an attacker can reach, and apply mitigations while patches are tested and rolled out.
In this post, we explain the vulnerabilities and their impact, and provide mitigation and detection guidance. Organizations should identify affected deployments and apply the security updates as soon as they are available. If upgrading is not immediately possible, temporarily disable HTTP/2.
NGINX can also serve web content directly and act as a load balancer, distributing traffic across multiple servers. A single NGINX deployment can serve several applications, making it a shared entry point for the websites and APIs behind it.
The Vulnerabilities
Both vulnerabilities are memory-safety issues in how NGINX handles HTTP/2 traffic. In CVE-2026-123633, a connection's memory is freed while a request still needs it, creating a use-after-free. In CVE-2026-123007, incorrect flow-control accounting leads to an invalid memory copy. Each can lead to unauthenticated remote code execution on the NGINX server.

Technical deep dive
CVE-2026-123633: An active connection marked as reusable
NGINX keeps a list of connections that it can close when it needs room for new ones. An HTTP/2 connection can join this list when it has no active requests, but must leave it when a request starts.
We start by sending only part of a HEADERS frame, which carries an HTTP/2 request's headers. With no active request streams,ngx_http_v2_handle_connection() marks the connection as reusable while waiting for the rest:
ngx_reusable_connection(c, 1);
if (h2c->state.incomplete) {
return;
}
When we send the rest of the frame,ngx_http_v2_create_stream() creates a request stream and increments h2c->processing. However, it does not remove the connection from the reusable list. We now have a request being processed on a connection that NGINX still considers safe to close.
Triggering the use-after-free
Next, we need NGINX to close this connection while the request is still running. Forwarding the request to an application server can trigger this.
Opening an upstream connection calls ngx_get_connection(). When free connection slots run low, ngx_drain_connections()selects reusable connections to close. Our HTTP/2 connection is still on that list, so NGINX can select it while processing its own request.
Before closing it, NGINX tries to send a GOAWAY frame to notify the client. Even creating this frame can fail, for example, if NGINX has reached its internal frame limit for the connection and has no frame available for reuse. In that case, the error path closes the connection and frees the memory associated with it. Processing then resumes in the original request, which still uses that memory. We have reached the use-after-free.
From use-after-free to remote code execution
The freed memory can now be reused for other data. The request-processing code still follows its old pointers, treating the new contents as the original request or connection.
This use-after-free can lead to unauthenticated remote code execution on the NGINX server.
HTTP/2 allows several requests, called streams, to share one connection. Flow control limits how much response data NGINX can send before the client is ready to receive more. NGINX tracks the connection's remaining allowance in a counter called h2c->send_window.
When NGINX queues response data, it subtracts that data's size from the counter before sending it. If a stream is canceled while its data is still queued, ngx_http_v2_filter_cleanup() removes the unsent data and returns the unused allowance:
h2c->send_window += window;
This refund does not check HTTP/2's maximum allowed window. If the client has already increased the allowance while data was waiting to be sent, the refund can push the counter above that maximum. NGINX is now tracking a value the rest of its HTTP/2 code assumes cannot occur.
A bounds check that no longer works
The next problem is in ngx_http_v2_state_window_update(), which checks whether an increase would exceed the limit:
if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window)
The check subtracts the current allowance from the maximum to calculate how much room remains. But the refund has already pushed the allowance past that maximum. Because the calculation uses an unsigned integer, which cannot represent a negative number, the subtraction wraps around and underflows to a very large positive value. The check now treats an invalid counter as though it has plenty of room left and allows further increases.
From an invalid length to remote code execution
The invalid counter eventually reaches ngx_http_v2_send_chain(), where it is converted to the signed integer type off_t to calculate how much data to send. A sufficiently large value becomes negative. That negative length then reaches the code that describes a portion of a response buffer, leaving its end pointer before its start pointer.
When the TLS send path in ngx_ssl_send_chain() processes this malformed buffer, further signed and unsigned conversions turn the invalid length into an out-of-bounds memory copy. An attacker can use this to disclose memory, corrupt the heap, and lead to unauthenticated remote code execution on the NGINX server.
We confirmed remote code execution with an ASLR bypass on official NGINX 1.31.7 and 1.31.8 builds. The tested path used HTTP/2 over TLS on 64-bit systems serving response data from memory. Ordinary static files can reach this path through standard TLS processing, without a backend application or third-party module.
Exploitation
To confirm these vulnerabilities, Wiz Research built proof-of-concept exploits and managed to run them in multiple lab settings against servers running common NGINX configurations we’ve seen in customer environments. In the interest of customer protection, we will not be releasing these exploits at this time.
Like other memory-safety issues, such vulnerabilities are difficult to exploit remotely and require the attacker to disclose memory addresses, groom and shape the heap correctly, and handle different NGINX versions, builds, and configurations. In reality, attackers may not need to target every single configuration, and we have seen in PHP2Shell that widespread attacks initially start against packaged products where many customers use the exact same build and configuration. Motivated attackers may tailor exploits for specific targets.
Any exploit assumes the attacker is able to communicate directly with the affected NGINX server. CDNs and WAFs that terminate HTTP/2 may mitigate parts of the exploit by not reflecting the exact payload back to the underlying NGINX server. This depends on implementation.
Specifically, CVE-2026-123007 requires the attacker to send a large number of WINDOW_UPDATE records to increase it to an arbitrary value. Detection rules covering long standing HTTP/2 connections sending large amounts of data may hint at an attack associated with this vulnerability. CVE-2026-123633 has different exploitation constraints and is more likely to be exploited when NGINX is configured in proxy configuration.

Conclusion
With NGINX handling traffic for critical websites and applications, the impact of flaws in its core extends far beyond a single service. This research is another example of AI uncovering critical vulnerabilities in widely deployed infrastructure. The flaws were already there; AI helped us find them.
As we saw with PHP2Shell, AI is changing the economics of vulnerability research. The same capabilities that help defenders uncover flaws can also help attackers investigate them. Software that has been used and reviewed for years still needs to be examined as these tools improve.
The opportunity is to make this work routine: finding vulnerabilities in the software organizations depend on and working with maintainers to fix them. Our collaboration with F5 brings that approach to NGINX, helping protect the applications and services behind it.

Does a Code-Tuned Embedding Model Pay Off? papr-embed-code-1 in Qdrant
Dylan Couzon, Anush
·
November 18, 2026
If you search code, you’ve probably asked this: is a code-specific embedding model worth it, or is a strong general one good enough?
Papr’s papr-embed-code-1 is a good test case. It’s Qwen3-Embedding trained further on code retrieval, with open weights in two sizes: 0.6B and 4B. Papr reports top scores on CoIR, a code retrieval benchmark. But it trained on most of CoIR’s training data, and its model card says so. Papr also reports the 4B at #1 on MTEB’s two held-out code leaderboards, RTEB (Code) and CodeRAG.
We asked a narrower question. Does it beat the model it started from on code it never saw? And what does it cost to run in Qdrant?
How We Tested
We compared each papr-embed-code-1 model with the Qwen3-Embedding model it was trained from, with the same query instructions. The tasks come in three groups:
- Code Papr didn’t train on: HumanEval and MBPP match a task description to the Python function that solves it. FreshStack matches a Stack Overflow question to the files of the library it’s about. WikiSQL matches a question about a table to its SQL query.
- Code Papr trained on: three CoIR tasks, though the 4B skipped CodeTransOcean Contest. APPS matches a programming problem to its solution. CodeTransOcean Contest matches a program to the same program in another language. StackOverflowQA matches a question to its answer.
- Prose: four BEIR datasets, NFCorpus, ArguAna, SCIDOCS, and FiQA.
Where Papr’s model cards score its own models, ours match to within 0.001 nDCG@10 on every task except the ones full of identical documents, marked † in the full results. There, the score depends on how ties break, which can change with batch size. On SyntheticText2SQL, we got 0.625 and 0.650 for the two sizes, against Papr’s 0.720 and 0.723.
Better on Code It Never Saw
On code Papr didn’t train on, both sizes beat their base model. The 4B gained 0.034 nDCG@10 on average, and the 0.6B 0.026. On the CoIR tasks, the gains were similar.
The gain held on every one of those tasks, but its size varied a lot. On HumanEval, the 4B base model already scored 0.98, so there wasn’t much left to gain. On WikiSQL, the 4B gained 0.070.
Prose went the other way. Both sizes scored a little lower than their base model, by 0.003 for the 0.6B and 0.016 for the 4B. On TREC-COVID, a set of COVID-19 research papers, the 0.6B lost 0.065. If most of what you search is prose, keep the base model.
Compressed to 1 Bit, the 4B Beats the 0.6B
Code search usually means a lot of vectors: a function, a file chunk, or a snippet each. The 4B’s vectors have 2,560 dimensions, which is 10 KB per vector in float32.
They compress very well. With 1-bit TurboQuant, each vector takes 328 bytes, 31x less. On our seven code tasks, 1-bit TurboQuant kept 99.7% of the 4B’s float32 score without rescoring, and all of it with rescoring at 2x oversampling.
That changes which model to pick. The 4B compressed to 1 bit scores higher than the 0.6B in float32, and takes 12x less RAM.
The 4B still costs more to run, because it embeds about four times slower than the 0.6B on the same GPU. And WikiSQL is the exception, where the 0.6B scored higher.
A Million Snippets in One Collection
Our other code tasks have at most 20,000 documents, which makes compression look easy. So we also loaded CodeSearchNet-CC into one collection: about a million snippets in six languages, from Python to Ruby. Each query is the start of a function, and the right document is the rest of it. A payload filter keeps the search within the query’s language.
Compression held up at this size. At hnsw_ef 128, 1-bit TurboQuant with rescoring kept 99.5% of exact search’s score, against 99.7% for float32. It was faster too, at 1.0 ms per query against 1.8 ms, with the original vectors for rescoring already in memory.
The bigger lever was hnsw_ef, the number of candidates the search explores. Raising it from 128 to 256 added 0.002 to 0.004 nDCG@10 to every setup. That’s enough for rescored 1-bit vectors at 256 to beat float32 at 128. At 256, float32, 2-bit, and rescored 1-bit vectors all kept 99.8% or more, and the 1-bit search took 1.4 ms against 2.9 ms for float32.
Dropping the filter and searching all six languages at once cost 0.005 to 0.007.
What About BM25?
Code is full of exact names, so keyword search seems like a natural partner. Qdrant 1.20 added a code tokenizer for full-text indexes. It splits getUserName and get_user_name into the same words. Qdrant can also score full-text matches with BM25, so a hybrid query can fuse BM25 with the dense search.
On our tasks, BM25 on its own was far behind dense search. On APPS, where the queries are problem statements and the documents are bare solutions, it scored 0.01 nDCG@10. The two share almost no words.
Fusing BM25 with dense search at equal weight made every task worse, by 0.02 to 0.17 for the 4B. Down-weighting BM25 helped, but only up to break-even. With BM25’s RRF weight at 0.1, the 4B averaged 0.0006 below dense search alone, and its best gain on any task was 0.002.
Our queries were questions, descriptions, and code, and for those, dense search alone was the better choice.
So, Does It Pay Off?
For code search, yes. On code it never saw, papr-embed-code-1 beat the model it started from at both sizes, by about 0.03 nDCG@10. On prose it did a little worse, so if most of your corpus is prose, stay with the base model.
The bigger choice is the size. Compressed to 1 bit, the 4B scored higher than the 0.6B in float32, in a twelfth of the RAM. If you can afford to embed with the 4B, we’d store it with 1-bit TurboQuant, keep rescoring on, and raise hnsw_ef before adding bits. Compare against an unquantized collection on your own queries, once with rescoring disabled and once with 2x oversampling. If you index several languages in one collection, filter by language.
We’d leave BM25 out to start. If your users search for exact identifiers, that’s the case to test it on, with a low weight.
The 0.6B is coming to FastEmbed in its next release.

A virus has stopped pancreatic cancer in its tracks in three people in a clinical trial in the US. Further evaluation is needed in larger trials, but the early results are encouraging, especially since only small doses of the virus were administered for initial safety testing.
“We only injected one-tenth of the dose we are eventually aiming at, so the efficacy is better than I expected, especially as this is pancreatic cancer,” says Masato Yamamoto at the University of Minnesota, who led the development of the viral treatment.
Pancreatic cancer is notorious for being the deadliest type of the condition. One reason is that symptoms tend to appear late, when the cancer has already spread and cannot be surgically removed. Once diagnosed, people usually live only around three to six months.

Another reason is that pancreatic tumours have tough, fibrous exteriors that block chemotherapy drugs from getting in. “They’re hard as hockey pucks,” says Yamamoto. Immunotherapies that boost immune activity against cancer are also ineffective, because pancreatic tumours can hide from the immune system.
The first patient in the trial, who had a pancreatic tumour 7 centimetres across, was administered the treatment a year ago, and the other two have been since then. At the time, their tumours hadn’t spread beyond the pancreas. Since being treated, their tumours haven’t grown any further. “They are all still alive and have clinically stable disease,” says Yamamoto, who presented the results at the annual meeting of the American Society of Gene and Cell Therapy in Boston, Massachusetts, earlier this month. Another 15 patients will now be given higher doses to find the optimum level.

The virus is an adenovirus that has been genetically engineered to replicate only inside tumours and not healthy tissue. Its replication is specifically activated by an enzyme called cyclooxygenase-2 (COX-2), which is present at much higher levels in cancer cells than in normal ones. After cancer cells become infected with the virus, they burst open and die, releasing more virus that can infect neighbouring cancer cells.
In the trial, the virus was injected directly into the patients’ tumours through a thin tube that was guided down a patient’s throat to their pancreas. The tube had an ultrasound probe on the end to allow visualisation of the tumours.
The reason the tumours have stopped growing but haven’t become any smaller may be due to the low treatment dose, says Yamamoto. He thinks they may start to shrink as the virus has more time to replicate.
As the tumour cells start to break apart and leak their contents, the immune system may also be able to recognise and fight the cancer, says Yamamoto. “The patient’s immune system can realise something is wrong, and then go and attack the tumour,” he says. The hope is that the immune system will also recognise and destroy any tumour cells that have spread to other parts of the body. If so, the treatment could be effective against metastatic pancreatic cancer.
To try to supercharge this natural immune response, Yamamoto and his colleagues are now planning to combine the viral treatment with immunotherapies like checkpoint inhibitors – drugs that block proteins that stop the immune system from attacking the cancer cells – in future clinical trials.
Adenoviruses, which cause cold- and flu-like symptoms in their unmodified forms, have a long history of being investigated as potential cancer treatments. In the 1950s, for instance, women with cervical cancer were injected with an unmodified adenovirus in a clinical trial, with partial success. However, it became clear that adenoviruses must be engineered to make them selectively target cancer cells, for safety and efficacy reasons.
The only cancer-killing virus that has been approved by the Food and Drug Administration in the US is T-VEC, a genetically modified herpes simplex virus that is injected directly into melanoma tumours, causing the cells to rupture and die.

phpAfterShell: From Interrupted Session Writes to Remote Code Execution
TL;DR: PHP can update a file-backed session while parsing an unauthenticated multipart request, even before the target script begins execution. We discovered reliable methods to interrupt the file operation during session upload-progress updates, allowing us to splice the prefix of one valid session with the suffix of another. A subsequent session operation treats the corrupted data as legitimate server-side state, giving attackers control over session values and the ability to trigger object deserialization. By chaining this primitive with a memory-corruption in a PHP-native class, we achieved remote code execution. We reported this vulnerability to the PHP team, and it was assigned CVE-2026-126714, with a critical CVSS score of 9.2.
php2shell drew attention to an unusual part of PHP’s request lifecycle: while PHP is still parsing an unauthenticated multipart request, before the target script even begins, the upload-progress callback can open and decode a file-backed Session. The original exploit took advantage of objects becoming active during this callback, and PHP addressed it by restricting class resolution during RFC1867 upload-progress updates.
When we started looking into the patched implementation, we were curious about what happened to the Session data beyond the deserialization step. Even with the new restrictions in place, the callback still reads the existing Session, adds upload-progress state, serializes the whole thing, and writes it back to the same file. In other words, while the patch changed which objects could be created in memory, the underlying file update behavior remained untouched. This raised a different question: what actually happens to the Session file if the PHP worker dies in the middle of an update?
To answer that, we had to look beyond the PHP code itself. PHP serializes the updated Session into a valid value, but the file handler writes it to the existing inode using pwrite() and ftruncate(). These operations are not atomic, and an interrupted update doesn’t necessarily leave the file in either its old or new state. Depending on where the interruption happens, part of the new Session may already have been written while bytes from the previous Session remain on disk. The result can be a Session file containing the prefix of the new serialized data and the tail of the old one. Both original Sessions are valid, and surprisingly, their combination can also be valid, but with a completely different meaning.
This is where things got interesting. By carefully choosing the length fields in the new prefix, an attacker can make PHP’s Session decoder interpret leftover bytes that were previously just part of an ordinary string as separate Session entries and serialized objects. Nothing needs to be deserialized during the upload-progress callback itself. The attacker only needs to leave the right bytes on disk and wait for the application to call session_start(), at which point PHP reads the modified Session and deserializes those objects.
This gave us a new exploitation path that the php2shell patch did not address. The patch prevented objects from becoming active during the RFC1867 callback, but it couldn’t prevent an interrupted file update from leaving behind a different, valid Session. What began as a closer look at a PHP patch eventually led us through the Session serialization format, the file handler’s write behavior, and all the way down to how the kernel handles interrupted buffered writes.
Before the Script Begins
Most PHP developers meet file uploads through $_FILES. By the time application code reads that array, PHP has already parsed the multipart body. The work happens during request startup in the RFC1867 parser.
RFC1867 emits events as it encounters form fields, file headers, file data, and the closing boundary. The Session extension subscribes to those events when upload progress is enabled. A field named PHP_SESSION_UPLOAD_PROGRESS supplies a progress token. PHP then resolves the request’s Session ID, initializes the Session module, and writes progress information before index.php executes its first line:
php_rinit_session(0);
PS(id) = zend_string_copy(Z_STR(progress->sid));
...
php_session_rfc1867_update(progress, 0);
At the start of a file part, the callback constructs a Session value containing byte counters and file metadata. The multipart field name and filename become strings inside that value:
upload_progress_<token> => [
"content_length" => ...,
"bytes_processed" => ...,
"files" => [[
"field_name" => <multipart field name>,
"name" => <multipart filename>,
"tmp_name" => ...,
"error" => ...
]]
]
This gave us the first reachability result. An application does not need an upload controller or a call to session_start() on the multipart endpoint. PHP itself is the Session writer. A request only needs to reach the Web SAPI as multipart/form-data with upload progress enabled.
Two Request Paths, One Inode
The callback assigns the selected SID to PS(id). With session.save_handler=files, the upload request and a later application request resolve the same path of <session.save_path>/sess_<SID>
The first writer is RFC1867. It opens the file during multipart parsing, reads the current Session, adds or removes the progress key, serializes the result, and writes it back. The second writer is the application. When a later route calls session_start(), it opens the same file and decodes it into $_SESSION.
The default php Session serializer is used on both paths. Upload completion also removes the progress entry and flushes the whole Session again. Each progress update therefore operates on the complete file rather than an isolated progress record.
PHP takes an exclusive flock() while a worker owns the Session. That prevents cooperating workers from writing at the same time. It does not roll back bytes. If the worker disappears, the kernel releases the lock and leaves whatever the inode contains at that moment.
This shifted the question. Concurrency between writers was not required to mix two values. A single worker could modify part of the live inode and die before PHP finished the update.
A Session File Is a Parser Input
The file handler does not store a PHP array as one opaque blob. With session.serialize_handler=php, it concatenates records in this form:
session_key | serialized_value
The decoder scans to | for the key, then hands the following bytes to PHP’s unserializer. Once that value ends, the next byte starts another Session key. There is no file-level length, checksum, generation number, or commit marker.
A small Session may look like this:
username|s:5:"alice";
roles|a:1:{i:0;s:5:"admin";}
profile|O:8:"stdClass":1:{s:5:"theme";s:4:"dark";}
The productions become more significant as the parser moves from simple values to structured state:
- N, b, i, and d create scalar values.
- s carries a byte length. That length decides where parsing resumes.
- a carries an element count and recursively decodes its children.
- O, C, and E enter class reconstruction, custom serialization, or enum handling.
- R and r connect the new value to something decoded earlier in the stream.
The length fields supplied the missing piece. Bytes can be syntactically active at one offset and inert at another. A serialized object placed inside a sufficiently long string is only data. Change the length in a prefix, and the same bytes can become the beginning of the next top-level record.
This produced a concrete target. We did not need arbitrary file contents. We needed a prefix from replacement state R to move the decoder onto a chosen tail from carrier state C.
Following the Update into the Kernel
The file handler writes the serialized replacement into the existing Session inode with pwrite() at offset zero:
n = pwrite(data->fd, ZSTR_VAL(val), ZSTR_LEN(val), 0);
if (n != ZSTR_LEN(val)) {
return FAILURE;
}
At the PHP level, this looks like one operation. At the kernel boundary, a large buffered write may copy many pages into the page cache before the syscall returns. If the process dies during that copy, the inode can already contain a prefix of the new buffer. PHP never receives a short-write result because there is no process left to receive it.
Our first hypothesis used PHP’s execution timeout. It was attractive because the timer is remotely controllable through parser work. Tracing showed why the early experiments were inconsistent. On our Linux test systems, the timeout became actionable after the buffered pwrite() returned. The file contained all of R, not a partial prefix.
That failure narrowed the problem. To interrupt the copy itself, the worker had to disappear inside the syscall. An OOM kill supplied that behavior for one family of releases. A separate source change created another family where a complete pwrite() was enough because truncation happened in a later syscall.
Timeout delivery and an uncatchable OOM kill interact differently with a buffered pwrite().
The root cause stayed the same in both cases. PHP updated the live inode in place and treated completion of several filesystem operations as one logical Session commit.
Two Ways to Keep the Old Tail
Let C be the carrier Session already stored on disk and R the replacement PHP wants to commit. The order of pwrite() and ftruncate() creates two exploitable states.
Overview: the two interruption points produce different combinations of replacement R and carrier C.
Variant A: The Write Stops Partway
In the first ordering, PHP truncates before writing only when the replacement is shorter than the size cached when the file was opened:
if (ZSTR_LEN(val) < data->st_size) {
php_ignore_value(ftruncate(data->fd, 0));
}
n = pwrite(data->fd, ZSTR_VAL(val), ZSTR_LEN(val), 0);
if (n != ZSTR_LEN(val)) {
return FAILURE;
}
If R is at least as long as C, the old inode remains in place when pwrite() begins. A worker killed after copying k bytes leaves:
R[0:k] || C[k:]
Variant A: termination during pwrite() leaves a prefix of replacement R joined to the retained carrier C tail.
The useful insight was that k did not need to be one exact offset. We shaped the serialized grammar so that a range of partial prefixes reached the same retained record. This converted a narrow kernel event into a wider parser acceptance interval.
Variant B: The Write Finishes Before Truncation
A later ordering writes first and truncates the old tail only after pwrite() reports success:
n = pwrite(data->fd, ZSTR_VAL(val), ZSTR_LEN(val), 0);
if (n != ZSTR_LEN(val)) {
return FAILURE;
}
if (ZSTR_LEN(val) < data->st_size) {
php_ignore_value(ftruncate(data->fd, ZSTR_LEN(val)));
}
When R is shorter than C, a complete write temporarily creates:
R || C[|R|:]
The next syscall removes the tail. If the worker terminates after pwrite() and before ftruncate(), the temporary state becomes durable.
Variant B: a complete shorter pwrite() leaves the carrier C tail until ftruncate().
This changes the exploitation problem. Variant A needs termination during a buffered copy. Variant B needs termination between two syscalls. The second window is still small, but it no longer depends on a partial kernel copy.
Commit c2b02f24dff separates these orderings in the affected source history.
Building a Third Valid Session
The carrier Session C contains the target record inside a length-delimited string. Parsed on its own, the object bytes are inert. The replacement R changes the grammar immediately before the retained tail. After an interrupted update, the decoder reaches the tail as a new top-level Session key.
C: [ordinary records][string length -------- object bytes as data --------]
R: [replacement prefix][shorter string length]
mix:[replacement prefix] [object bytes as a Session record]
Both source states are generated by PHP from ordinary multipart fields. Neither source file is malformed. The malformed state exists only at the storage boundary, where bytes from the two serialized values meet.
The public proof uses a harmless object:
evil|O:8:"stdClass":1:{s:5:"proof";s:5:"pwned";}
A later route contains only normal Session code:
<?php
session_start();
var_dump($_SESSION['evil'] ?? null);
If the splice misses early, the consumer sees the carrier state. If it misses late, it sees the replacement. A hit creates $_SESSION['evil'] as a real object. Those three outcomes gave the exploit a stronger oracle than socket timing alone.
Finding the Windows over HTTP
A fixed delay worked on one machine and failed on another. CPU speed was only part of the reason. Apache scheduling, page-cache state, allocator pressure, multipart parsing, and the exact moment a worker crossed its limit all moved the boundary.
We stopped treating the interruption point as a constant. The controller treated it as a moving boundary that could be measured through application state.
Each candidate uses a fresh SID and three requests against the same sess_<SID> file:
- A carrier POST writes C through upload progress.
- A replacement POST asks the same callback to write R.
- A consumer GET calls session_start() and classifies the resulting Session.
Remote calibration: carrier C, replacement R, and the consumer oracle across both write windows.
The HTTP connection tells us whether a worker completed or disappeared. The consumer tells us what happened to the file. Together they distinguish an early termination, a late termination, and a splice that crossed the parser acceptance interval.
Calibrating Variant A
For the partial-write family, held multipart requests bring the Apache cgroup close to its memory boundary. The carrier and replacement keep their important grammar at a fixed geometry. Two replacement lanes cross a barrier together so that an allocation in one worker can push another worker over the boundary while it is writing.
The controller adjusts pressure at two scales. Coarse slots move in 2 MB steps. A tunable request covers the smaller interval between them. Complete responses and disconnected sockets feed a rolling history. Stable observations move the coarse allocation count. Mixed observations are fitted with a recency-weighted logistic model, then sampled near the estimated transition at 32 KiB offsets.
The model handles a mismatch between two kinds of state. The memory limit is discrete from the attacker’s perspective, while the amount already committed by Apache and PHP is noisy. Re-estimating the transition after each observation is faster than scanning the full range again. Dead pressure connections are replaced so the controller keeps approximately the same background state.
Variant A calibration loop: coarse pressure, a fine allocation, synchronized replacement lanes, and a recency-weighted boundary estimate.
Kernel probes showed partial prefixes near 2 MiB, 4 MiB, and 5.5 MiB. The grammar accepts a span around those regions. In a fresh HTTP run, the promoted object appeared on attempt 11.
Calibrating Variant B
The post-write window needs a different control variable. A legal multipart field name containing repeated bracket notation makes PHP spend CPU in request parsing before it flushes upload progress. The field name never enters the carrier record, so its depth changes timing without changing the target grammar.
Shallow inputs terminate before the replacement is written. Deep inputs pass the truncate. Between them lies the state where pwrite() has completed and ftruncate() has not.
The full depth range is not perfectly monotonic. We first locate a small region where outcomes are locally ordered. A particle filter then tracks the boundary. Its state includes drift and an outlier component because neighboring requests can land on different Apache scheduling histories. Surprise-driven updates widen the search after an unexpected result. Systematic resampling keeps candidates concentrated around the most informative depths.
Variant B calibration loop: bracket a local phase axis, probe one depth, classify the Session, and update the particle population.
This approach raised the simulated 24-attempt hit rate from 52.8% to 88.4%. A fresh HTTP run reached the target state in ten attempts after one coarse rebase. The controller learns the current host instead of carrying a timing constant from the development machine.
The Next Request Changes the Meaning of the Bytes
The interrupted upload leaves the mixed file in session.save_path. The next request presents the same SID and calls session_start(). PHP reads the file as trusted server-side Session state and runs the normal decoder.
The earlier php2shell remediation restricts class resolution while the upload-progress callback is active. On patched builds, an object handled during that callback is transported as __PHP_Incomplete_Class. Its serialized representation still reaches the file handler. Once RFC1867 has finished, the restriction is gone. A later session_start() resolves the promoted record through the ordinary class path.
The splice is useful before objects enter the picture. Scalars and arrays can replace identity, authorization, CSRF, password-reset, cart, or workflow state before application code performs its access checks. An object adds a path into magic methods and native decoders.
At this point the storage bug becomes an arbitrary deserialization primitive. The application contributes only its normal use of Sessions.
From a Native Object to RCE
PHP ships internal classes that reconstruct native state from serialized input. SPL containers, iterators, date and time objects, random engines, and extension-owned wrappers cross from PHP values into C structures. Their decoders manipulate zend_object, HashTable, references, native pointers, property tables, and length fields.
We audited that surface as a separate problem. The Session file could carry an object. The remaining question was how much power PHP’s own classes exposed when an attacker controlled its serialized representation.
That audit produced a chain using native PHP decoders. A memory-corruption vulnerability supplies the first primitive. Later stages disclose the addresses required by the worker and redirect an internal call. The object promoted from the Session tail enters the chain during session_start() and ends in code execution inside the PHP process.
The decoder and final heap layout remain reserved for coordinated disclosure. The full chain does not depend on an application-defined gadget class.

On Exploitation and Remediation in the AI Era
Over the years, PHP security research has produced all kinds of interesting tricks, often far more memorable than the vulnerabilities themselves. Deserialization techniques evolved from userland gadget chains to PHP-native objects and unexpected entry points like PHAR metadata. Researchers have found clever ways around open_basedir and disable_functions, while combinations of php://filter and character encoding tricks turned seemingly limited LFI vulnerabilities into RCE. Many of these techniques also came out of CTFs, where unusual constraints pushed researchers to explore obscure PHP behaviors and combine things that weren’t originally meant to work together. Much of this work happened long before AI became part of security research, through manual code review, experimentation, and a lot of trial and error. What really gets researchers excited has never been another CVE number or a single bug. It’s those clever tricks that connect things nobody thought were related, or make something that seemed impossible actually work.
AI changes the pace of that work. A model can hold more of the codebase in view at once, keep several competing ideas alive, and make it practical to run far more experiments than you would write harnesses for by hand. On this bug, fixed timing and pressure values kept failing whenever worker scheduling or memory state drifted; treating every HTTP attempt as an observation, estimating where the boundary had moved, and choosing the next request from that estimate only came together after iterating through multiple failed models and kernel probes that would have taken weeks to build manually.
Patching has become faster too, and this creates a new problem. AI can follow a known exploit, add a guard, and write a regression test in a short time. That patch may stop the exploit while leaving the deeper bug in place.
The php2shell patch is a good example. It stopped objects from becoming active during the RFC1867 callback. It did not make the Session file update safe when a worker died. The bytes could remain on disk and become active later, when the application called session_start(). The original exploit stopped working, but the underlying problem was still there.
At depthfirst, we do offensive research with a defensive goal: knowing whether the software we protect is genuinely safe after a patch lands, where a broken PoC is only the first check. When both finding a bug and shipping a fix can happen quickly, reviewing the patch deserves the same care as building the exploit, making sure remediation removes the reason the bug was possible rather than just blocking the first path that reached it.
Affected Versions
The source history divides into three groups. Earlier releases use ordinary object semantics during RFC1867. The first remediation changes object transport and retains the truncate-before-write ordering. Later branches move truncation after the write, which changes the interruption window without removing the retained-tail primitive.
