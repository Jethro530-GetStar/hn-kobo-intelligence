FULL TEXT

Article
An NES CPU compiled into the weights of a stock Qwen3.5 model.
The NES's 6502 CPU (the core of its 2A03 chip), its 2 KB of work RAM, and a cartridge's program
ROM run inside a standard Qwen3_5ForCausalLM checkpoint. Nobody trained these weights; a
compiler computed every one. When you play a game, the model predicts the CPU's execution log
one token at a time. A small host program plays the rest of the console around it: it draws the
picture, reads the controller, and fires the vblank interrupt.
nesformer builds on Qwenputer by Divyansh Agrawal, which compiled a CHIP-8 and then a RISC-V CPU into Qwen3.5-4B. It reuses Qwenputer's compiler and its central trick: the model's Gated DeltaNet state is the machine's memory.
| Super Mario Bros. (World 1-1) | Full Game by Doug Fraker (title screen and first level) |
|---|---|
Every CPU token in these runs came from the model. For the bundled test games, every frame also matches a conventional 6502 emulator's output exactly (see How it was checked).

the nesformer/ package, not inside it:

The CLI looks for weights/ beside the nesformer/ package. To keep the weights elsewhere,
pass --weights /path/to/weights to run, check or trace, or give the path to info.
To confirm the weights unzipped correctly, run shasum -a 256 -c weights/SHA256SUMS from the
top folder.
You need Python 3.11 or newer.
python3 -m venv .venv
source .venv/bin/activate # Windows: .venv\Scripts\activate
pip install numpy scipy numba pillowpython -m nesformer run roms/thwaite.nes --frames 600 --show \

--show draws each frame in your terminal as the model generates it. When the run ends, the CLI
saves an animated GIF named after the ROM (here thwaite.gif) in the current folder.
Expect it to be slow. The first run spends about 20 seconds compiling the engine with numba. After that, a frame takes 1–6 seconds, so 600 frames (10 seconds of NES time) take around 25 minutes.
Point run at any .nes file that uses the NROM board (iNES mapper 0), such as Super Mario
Bros., Donkey Kong or Excitebike. You supply the ROM; nesformer only ships the three freely
licensed test ROMs in roms/.
python -m nesformer run roms/smb.nes --frames 600 --show \
--buttons "start@60-65,right@200-600,a@250-265+300-315+360-375+420-435+480-495+540-555"
That script starts the game, then walks Mario right and jumps about once a second. The CLI loads the ROM into the model's state at startup, so the same weights run any NROM game without a rebuild. Games on other boards stop with a message: see Limitations.
--buttons takes a comma-separated list of entries. Each entry names one or more buttons joined
by +, then @, then one or more frame ranges joined by +:
start@60-65 press Start during frames 60 to 65
right@200-600 hold Right from frame 200 to frame 600
a@250-265+300-315 press A twice
right+b@200-600 hold Right and B together (run, in Super Mario Bros.)
The buttons are a, b, select, start, up, down, left and right. Frames count from
power-on at 60 per second, so frame 600 is 10 seconds in. Games ignore input on screens where
you can't move, so holding a button a little early does no harm. In Super Mario Bros., a longer
A press makes a higher jump.

run, check and trace all accept --weights, --engine, --buttons and --no-skip.
check --tokens N sets how far to compare (default 50,000). trace --tokens N sets how many
tokens to print (default 40). build --out DIR writes the checkpoint somewhere other than
weights/.
| In the model (weights + DeltaNet state) | In the host ( nesformer/host.py) |
|---|---|
| The 6502 core: all 151 official opcodes, every addressing mode, flags, stack, BRK and NMI entry | The PPU: a scanline renderer and the palette |
| 2 KB of work RAM | Controllers; APU registers (written, otherwise ignored) |
| 32 KB of PRG-ROM, stored twice: one copy for instruction fetch, one for data reads | NMI timing at vblank, injected as an NMI token |
| OAM DMA reads (the 256 bytes appear as DM tokens) | Answers to I/O reads, injected as IN tokens |
This split follows Qwenputer's CHIP-8 build, whose host injects timer ticks and draws the display from the trace. The host never sees the CPU's registers or RAM except through the trace.
The memory trick works like this. Each DeltaNet head keeps a 128 × 128 state matrix that the delta rule updates at every token. With the gate held open and a one-hot key, an update overwrites exactly one row of that matrix, and a one-hot query reads it back. So every row is a memory cell, and the cartridge, RAM and registers all live in rows.
weights/ is an ordinary Hugging Face folder. It loads with
Qwen3_5ForCausalLM.from_pretrained and needs no custom code.
| Architecture | Qwen3_5ForCausalLM, with Qwen3.5-4B's DeltaNet head shapes (16 key heads, 32 value heads, dim 128) and MLP width (9,216) |
| Layers | 7 Gated DeltaNet layers (the circuit), plus 1 all-zero attention layer that Hugging Face's cache needs |
| Hidden size | 768 |
| Vocabulary | 263,808 tokens |
| Parameters | 466.6M in bf16 (933 MB), of which 9.3M are nonzero, so the weights zip to 3.3 MB |
nesformer.json records which layer and head holds each part of the machine. A run writes the
cartridge, registers and RAM into those DeltaNet states, then decodes greedily.
| Layer | Attention (state) | MLP |
|---|---|---|
| 1 | PC anchor; instruction counters; A, X, Y, SP; flags N V Z C I D; pointer latches; NMI flag | counter thermometers; SP ± 1; LO + Y |
| 2 | — | PC = anchor + bytes executed since; PC + 1, PC + 2 |
| 3 | PRG fetch: opcode and two operand bytes at the PC | opcode decode; operand bits; indexed sums; branch test and target |
| 4 | — | effective address, by addressing mode and record stage; the byte a push stores |
| 5 | RAM and PRG data reads at the effective address | operand; ADC/SBC adder, compares, BIT; address decode |
| 6 | — | result byte, carry, overflow, flags, jump targets |
| 7 | — | the next token |
Each instruction becomes a record, and the record's last token commits it. As in Qwenputer's RISC-V core, the PC is implied rather than written: each final token carries its instruction's length, three DeltaNet counters tally the instructions of each length since the last jump, and the PC is the jump target plus that offset. Excerpts from Full Game:
SEI P(000100 px0 L1)
LDX #$40 X($40 c0 v0 px0 L2)
STX $4017 IOW($4017=$40 L3)
TXS S($FF L1)
BIT $2002 IOR($2002) IN($00) P(000110 px0 L3) <- the host injects IN
BPL $8017 J($8017)
JSR $8279 PSH($FE) PSH($FD) J($8279) <- the return address is pushed in-circuit
RTS PUL($FC) LO($7B) PUL($FD) J($827C)
STA ($72),Y LO($08) HI($03) ST($00 a7=0 L2) <- pointer bytes latched, then the store
STA $4014 IOW($4014=$02 L0) DM(0:$FF) … DM(255:$00) NT(L3) <- OAM DMA
Most instructions take a single token; real game code averages 1.1–1.3 tokens per instruction.
nesformer/spec.py documents every token family.
- The reference CPU (nesformer/cpu.py) matches nestest's golden log for 3,348 instructions,
and the py65 emulator on 5.7 million instructions of game code.
- The exact circuit, run in Qwenputer's evaluator with its bf16 exactness checks, predicts every reference token: all of nestest plus 283,610 positions of two games' boot sequences.
- The checkpoint in stock transformers (bf16, CPU) predicts 2,651 positions of nestest and Full Game with no mismatches.
- The weights, free-running, generate traces identical to the reference CPU's: Run Tokens Frames NES time Result nestest (official opcodes) 4,586 — — identical, ending in the expected HALT Thwaite, check700,000 271 4.5 s identical trace and frames Thwaite, run1,916,527 600 10.0 s all 300 saved frames match Full Game, run2,645,885 420 7.0 s all 210 saved frames match
- The idle-loop skip changes nothing visible: frames and I/O writes, cycle timestamps included, match a run without it.
The default engine computes Qwen3.5's forward pass from model.safetensors, compiled with numba
and skipping the all-zero blocks. It ran at about 1,650 tokens/s on one CPU core of the machine
it was built on. The plain numpy engine does about 210, and stock transformers about 10. A real
NES would need about 700,000 tokens per second.
Games spend most of each frame in a loop that waits for vblank. When the host sees a loop body repeat exactly, with no RAM or I/O writes, it advances the clock to just before the next PPU event, and the remaining iterations still run. That cuts the token count by 2.6× to 4.2×. Overall, nesformer runs 150–290× slower than the real console.
- NROM cartridges only (iNES mapper 0). The CPU can address only 32 KB of program ROM at a time. Bigger games carry a bank-switching chip (a mapper, such as MMC1 or MMC3) that swaps which part of the ROM the CPU sees. nesformer's ROM reads happen inside the model, from a fixed 32 KB table, so it can't follow a bank switch yet. Supporting a mapper means storing the whole ROM in the state, keeping the bank registers there too, and adding one stage that turns each CPU address into a ROM address.
- Official opcodes only. An unofficial opcode emits HALT.
- Code must run from the cartridge ROM. A jump into RAM emits HALT.
- No IRQs (APU frame IRQ, DMC). BRK and NMI work.
- Read-modify-write instructions on I/O registers don't produce an I/O write, and $4020–$7FFF reads as 0 (no PRG-RAM).
- The PPU and APU aren't in the weights. The PPU renders one scanline at a time, so mid-scanline effects aren't reproduced. Sprite-0 hit and sprite overflow are approximate, and there's no sound.

7. Cloudflare Turnstile solver library (no headless browser required)

Article
cfsolve is a Rust library and command line tool that solves Cloudflare Turnstile
widgets and challenge pages without a headless browser. It returns a Turnstile
token for widgets or a cf_clearance cookie for challenge pages.
Turnstile widgets can be solved using the page URL, the sitekey, and optionally the page's HTML (this should not be required in most cases). Challenge pages require a direct fetch or the HTML of the page.
cfsolve impersonates a specific browser, described by a profile file. One is
included: profiles/safari-26-ios.json (Safari on iPhone).
Each profile references recorded responses to the challenge's browser checks,
stored as JSON in a directory. Keep each profile with its directory when you
copy. Producing these files requires some manual (or AI) effort though it can
be greatly aided by solving challenges in a real web browser with the proxy
set to the address of a running capture-proxy, which records the decoded
payloads sent to Cloudflare. Currently only Safari and Chrome(ium) profile
types are supported.
You need the Rust version pinned in rust-toolchain.toml, plus CMake, a C/C++
compiler, libclang, and Git (to patch and build BoringSSL).
cargo build --release --bin challenge./target/release/challenge --page 'https://example.com/login' /tmp/solve \
--solve --fingerprint profiles/safari-26-ios.json
On success it prints the token (or cf_clearance=...) and sends progress
to stderr. The directory argument holds all requests and responses for
debugging, so it must be empty or not exist yet.
By default it solves the first Turnstile widget on the page, or clears
the challenge page. To pick one widget when the page has several, pass its
sitekey, with its action and cData when the site sets them. With --sitekey,
it fails on a challenge page.
./target/release/challenge --page 'https://example.com/login' /tmp/solve \
--solve --fingerprint profiles/safari-26-ios.json \
--sitekey 'SITEKEY' --action 'login' --cdata 'CUSTOM_DATA'
If you only have a sitekey, add --blank-page and set --page to the
site's real URL.
| Option | Description |
|---|---|
| --fingerprint <file> | Browser profile file to use. Required. |
| --page <url> | The page with the widget, or the challenge page. |
| --solve | Solve the widget or challenge. Without this, cfsolve stops after sending the widget's first payload. |
| --sitekey <key> | Select a widget by sitekey. |
| --action <value>, --cdata <value> | Override the widget's action and cData. This needs --sitekey. |
| --blank-page | Skip loading the page. Render the widget on a blank page at the page URL. This needs --solve and --sitekey. |
| --proxy <url> | Send every request through an http://, https://, socks5://, or socks5h:// proxy. Put credentials in the URL, as in socks5h://user:password@host:1080. |
| -h, --help | Show help. |
Add cfsolve as a path dependency and copy its [patch] section, since
Cargo only reads patches from the top-level Cargo.toml:
[dependencies]
cfsolve = { path = "/path/to/cfsolve", default-features = false }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
[patch.crates-io]
btls-sys = { path = "/path/to/cfsolve/vendor/btls-sys" }
wreq = { path = "/path/to/cfsolve/vendor/wreq" }
http2 = { path = "/path/to/cfsolve/vendor/http2" }
default-features = false turns off the internal tools so only the solver remains.
Use the Rust version in rust-toolchain.toml or newer.
use cfsolve::{Browser, Options, PageSource, Turnstile};
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
let browser = Browser::read("/path/to/cfsolve/profiles/safari-26-ios.json")?;
let options = Options::default();
let turnstile = Turnstile {
url: "https://example.com/login".parse()?,
page: PageSource::Navigate,
widget: None,
};
let token = browser.solve_turnstile(turnstile, &options).await?;
println!("{token}");
let cleared = browser.clear(&"https://example.com/".parse()?, &options).await?;
println!("cf_clearance={}", cleared.clearance);
println!("{} cookies; protected page: {}", cleared.cookies.len(), cleared.page.url);
Ok(())
}
Load a Browser once and share it. Concurrent operations each get their own
connections and cookies.
Send the cf_clearance cookie from the same IP address and user agent
as the profile, or Cloudflare will reject it.
PageSource::Navigate fetches the page. With only a URL and sitekey, use
PageSource::Blank and specify the widget:
use cfsolve::{PageSource, Turnstile, Widget};
let turnstile = Turnstile {
url: "https://example.com/login".parse()?,
page: PageSource::Blank,
widget: Some(Widget {
sitekey: "SITEKEY".into(),
action: Some("login".into()),
cdata: None,
}),
};
let token = browser.solve_turnstile(turnstile, &options).await?;
Set action and cdata to the values the site uses, or None when the site
doesn't set them. You can also pass a Widget with PageSource::Navigate to pick
one widget out of several or to supply one the site adds with JavaScript.
For a page you have already loaded, such as one behind a login, pass its URL and HTML:
PageSource::Html {
html: std::fs::read_to_string("account.html")?,
referrer_policy: None, // Or the response's Referrer-Policy header.
}
The widget runs in a cross-site iframe, so you don't need your login cookies.
With Html, widget: None solves the first widget on the page, while Blank
always needs a Widget and renders it on a blank page at the site's URL.
browser.clear(&url, &options) fetches the page and clears the challenge. The
Clearance it returns contains the cf_clearance cookie, all cookies for the
page, and the protected page. It fails with Error::NotChallenged when there's
no challenge.
If you fetched the challenge page yourself, pass the response as a
FetchedPage to browser.clear_fetched(page, &options). Use the same IP and user
agent as the profile.
If you don't know whether a URL shows a widget or a challenge page, use
browser.solve, which covers both cases:
use cfsolve::Outcome;
match browser.solve(&url, &options).await? {
Outcome::Token(token) => println!("{token}"),
Outcome::Cleared(cleared) => println!("cf_clearance={}", cleared.clearance),
}
Set a proxy per operation through Options, using HTTP, HTTPS, or SOCKS5:
let options = cfsolve::Options {
proxy: Some("socks5h://127.0.0.1:1080".into()),
..Default::default()
};
Library operations are silent by default. For progress messages and debug files,
implement Sink and set options.sink to Some(Arc::new(your_sink)).
| Error | Cause | Retry? |
|---|---|---|
| Error::Network | Connection failed. | Yes |
| Error::Rejected | Cloudflare rejected the solution. | Yes |
| Error::Blocked | The site returned an error page instead of a challenge. | No |
| Error::Challenged | You asked for a Turnstile token but got a challenge page. | Yes, after clearing it |
| Error::NotChallenged | You asked for a challenge clearance but there was no challenge. | No |
| Error::Config | Invalid profile or options. | No |
| Error::Unsupported | Any other failure, such as a new challenge build or a page with no widget. | No |
MIT, except for the patched dependencies in vendor/, which keep their own
licenses.

9. Arcan: A Farewell to Hubs
FULL TEXT
1 points · 1 comments · ingenieroariel
arcan-fe.com
New #2
Original article · HN discussion
Article
Those of you who have read the final sections of the article on Arcan: 10 Years of Online Obscurity know that I am anything but happy with the current state of computing affairs and its trajectory. The value that the current Internet holds to me is closing in on not being worth the cost.
In this post I will lay out the ongoing work on detaching from a terminally online life, and how the project will be maintained once the fabled 1.0 release hits. This is still ongoing, and not something I would dare to suggest that you consider for your own projects.
Poison The Well
It has been a little over 3 years since we switched to Fossil as our SCM of choice and a year and a half since we started mirroring and exporting to Codeberg after Microsoft decided to go from plain rude to straight up abusive, prompting a stronger response than ‘This repository has been archived’ — one more in line with Principle 6.
Fossil was a fairly easy choice as the command-line tooling is simply better than Git (which is not to say much) but mainly because metadata like wiki and commentary is not decoupled from the code repository itself, and in a world where the web is completely broken we can still continue via sneakernet even.
Due to dangling distribution packaging references the latest release was kept as a tag on GitHub, but general exporting stopped and keys for committing to the master branch were handed over to our resident slop jockey, let us call him Pablo. He threw together a plan.md for shifting it towards a “Capture the Flag exercise in deception”, making increasingly volatile changes.
While it was incredibly tempting to just go full Kachzynski with the whole thing, we ended up settling on smaller gradual changes that would not cause harm to anything that would clone / build and run it, but visible enough that it would be possible to see that they made it into the various knowledge cutoffs of frontier models, and get a feel for what the actual distance and impulse response was between fact turning into fiction by periodically checking both local models and those of the online abuse cartel.
Pablo meanwhile had some ‘work incentive tokens’ to burn (or else …) and ran a little project of his own accord. Over the course of a few months he had a fork with the code base translated to Zig, a Vulkan renderer, and a bootable statically linked image of the full stack running on a Mac M1 Studio with an Asahi kernel. Sure, the codebase is completely unmaintainable; about five times bigger than it should be, and several of the carefully managed subtleties were completely wiped out by the stroke of a prompt.
The results are arguably worse in both time, compute cost and results than what a competently written 90s-style source-level translator would have produced in seconds, at least for the Zig part. But Pablo is happy, and that counts for something, so that is now the content of the GitHub repository. If a schizophrenic lossy resampling of code lifted without consent or provenance is your idea of the future, that seems to be the place to call ‘home’. I will not be there. Do keep training your models on it though, and perhaps don’t trust the documentation too much.
There are a couple of mildly amusing side effects to this that I will keep to myself, but it is somewhat surreal to see the dissonance in G👀gle search results returning one idea of what Arcan is up to, and its LLM summary just above contradicting it with equal amounts of confidence.
Retooling
Abusive code forges are not new to us; we left SourceForge when they started injecting ads in our installer binaries. I do not believe in the future of any centralised forge, however; they were mainly a necessary evil for discovery to begin with.
Since discovery is dying along with its conjoined twin search, and link aggregator sites turning into slop and meta-slop steered rightward by play-pretend centrists anyhow, we need a different plan for how to work on Arcan and its related projects.
Since we are a small, tightly-knit team with only the occasional one-off contributor, the main concern is to have a low barrier to entry for submitting tickets and patches in a way that requires no additional tooling or account creation, but that can still be controlled for abuse and rate-limited, filtered and triaged with the occasional poison pill for known scrapers when they come a-knocking.
The basic building block already comes with an arcan build, namely arcan-net. This is still being tested out, but the short flow is easy enough:
arcan-net --get-file .priv .patch mypatch.template arcan.divergent-desktop.org
Fill it out according to the instructions inside it, and submit it with --put-file. The same procedure applies for tickets, but .patch is replaced with .ticket. The server-side configuration for this is similarly trivial:
config.lua:function ready() hook_resource(".patch", 0, "*", "/path/to/a12dir_patch.rb", "patch", "--patch-dir", "/where/to/store", "--template", "/path/to/patch.template" )end
Combined with the script from tools/a12dir_scripts. The crash recovery call trace captures in Durden will soon also be able to do this with a click of the submit button, and they are usually enough to fix whatever is going wrong.

For bot integration and CI testing I have an inotify/kqueue trigger that notifies the relevant VM runners, but they lack a coordination mechanism. This brings us to the final part of the equation.
