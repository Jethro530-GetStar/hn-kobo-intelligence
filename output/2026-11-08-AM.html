1. Show HN: Coldframe, a honeypot that poses as a supermarket fridge controller

A honeypot for supermarket refrigeration controllers.
In 2026, attackers broke into internet-facing refrigeration supervisors across Europe using default passwords and old, unpatched firmware, then forced defrost cycles. coldframe pretends to be one of those controllers. It records who connects, what passwords they try and which public exploits they use, and it never gives them anything real.
It is one Python file with no dependencies outside the standard library.
| Persona | Pretends to be | What it serves |
|---|---|---|
| danfoss | Danfoss AK-SM 800A system manager | StoreView login, a fake store dashboard, the XML API at /html/xml.cgi and /xml.cgi, HTTP and HTTPS |
| dixell | Copeland/Dixell XWEB EVO supervisor | Login page and the XWEB 500 CGI paths targeted by public exploits |
The Danfoss persona copies what internet scanners record for real AK-SM 800A units: the nginx server header and header order, the Danfoss StoreView page title, TLS 1.2 only, and a 1-year certificate for CN=DanfossSM800A issued by a SelfSigned-DanfossSM800A authority. Each build generates its own keys.
Weak logins (for example Supervisor / 12345) and a correct CVE-2025-41450 "code of the day" succeed. The attacker gets a session token and a dashboard of fake refrigerated cases with defrost buttons. Every action they take is logged as a control event; nothing is real.
The Dixell persona follows real XWEB EVO units the same way: no Server header, their security-header set and order, the same asset paths and page size. Its login uses the real /cgi-bin/login.lua flow: the documented factory login Admin / Admin succeeds, five failures in five minutes lock the user, and attempts at the XWEB Pro auth_mode bypass (CVE-2026-25085) are tagged.
Real units of both vendors serve their own favicon, and scanners match devices by its hash. That icon is the vendor's artwork, so it is not in this repository. For a private deployment you can point FAVICON_FILE at a copy you have the right to use.
The same goes for the Danfoss start page. Real units serve a short Angular loader page from the firmware, and thousands share its exact hash. Point INDEX_FILE at that index.html (from the public firmware package) and the decoy serves it byte for byte, with its original date in Last-Modified and ETag. The loader's main.*.js then shows the decoy's own login page, laid out like the firmware's remote login. If the firmware's assets/images/Danfoss-logo.png sits beside that index.html, the page uses it.
Both personas can also run an optional Modbus TCP service with fake case temperatures, setpoints and a defrost register. Real AK-SM 800A units only use Modbus to talk to their own case controllers, so Modbus is off by default. Turn it on to catch generic industrial scanners.
Requests that match a public exploit get an exploit field in the log:
- CVE-2023-25914: AK-SM 800A path traversal via get_file
- CVE-2023-25915: AK-SM 800A command injection via load_cert
- CVE-2025-41452: AK-SM 800A nginx header overwrite via load_nginx_headers
- CVE-2025-41450: AK-SM 800A "code of the day" login bypass (getauth with eds_only or quantum_only), noting whether the attacker computed the correct code
- SM800 code-of-the-day bypass: eds_only / quantum_only on other commands
- CVE-2021-45420: XWEB 500 upload and command paths under /cgi-bin/
- CVE-2026-25085: XWEB Pro login bypass via an unexpected auth_mode
PERSONA=danfoss HTTP_PORT=8080 python3 -I honeypot.py
Open http://localhost:8080 and every request shows up as a JSON line on stdout and in events.jsonl.
Run the tests (they start the honeypot on loopback and attack it):
python3 -I test_honeypot.py
Create an Ubuntu 24.04 server (a $4 DigitalOcean droplet is plenty) and paste cloud-init.yaml into the User data box. Change PERSONA=danfoss to dixell if you want the XWEB persona. About two minutes after boot the decoy is listening on port 80 (and 443 for Danfoss), hardened as below.
Then, in your provider's firewall, allow only the decoy's ports from anywhere and SSH from your own address. Read the log with:
ssh root@<server> 'podman logs coldframe'
Build the container. Each build makes a fresh self-signed certificate, so two deployments never share one.
podman build -t coldframe .
Run it with rootful podman or Docker. Rootless port forwarding rewrites the source address, which makes every attacker look like the same internal IP.
--userns=auto maps the container to an unused host UID range, so even the container user is nobody on the host. Podman needs a range to hand out, once per host:
echo "containers:2147483647:2147483648" | sudo tee -a /etc/subuid /etc/subgidsudo podman run -d --name coldframe --restart=always \
--read-only --cap-drop=ALL --security-opt no-new-privileges --userns=auto \
--memory 128m --pids-limit 512 --log-opt max-size=10m \
-p 80:8080 -p 443:8443 \
-v coldframe-logs:/logs:U \
-e PERSONA=danfoss \
coldframe
For Modbus, add -e MODBUS_PORT=5020 -p 502:5020.
On the host, only expose the ports the persona would really have, and block outbound traffic except DNS and package updates: the decoy never needs to connect out. Keep SSH reachable only from your own address: a fridge controller with SSH open to the world looks wrong.

summary.py turns a log into a short report:
python3 -I summary.py --hours 24 --ignore <your-own-ip> < events.jsonl
- It never runs commands, reads files, or forwards traffic. Exploit payloads are logged and dropped.
- Request bodies, logged fields and connections are capped, including a per-source limit so one attacker cannot crowd out others. Idle sockets time out, and the event log rotates once it gets large.
- Connections that trickle data to stay open are cut after 30 seconds, and refused connections are logged.
- Over-long log lines are truncated, and summary.py neutralises terminal escape codes from attacker input.
- The container runs as a non-root user in its own user namespace, on a read-only filesystem with no capabilities.
- Log fields are attacker-controlled. Treat them as untrusted when you view or process them.
- Shallow interaction. Logged-in attackers see a small dashboard and a handful of XML commands, not the full StoreView app.
- Public code can be fingerprinted. Anyone can read this repository and spot its exact responses. Change the persona strings, page layout and certificate subject for your deployment.
- Unconfirmed details. Static paths, the full web app and some XML response shapes of real units are not public. Where they were missing, coldframe uses plausible values.
- Cloud IPs look suspicious. Some scanners flag industrial devices on cloud hosting as likely honeypots.

2. The end of Microsoft Research's AI Frontiers group
FULL TEXT
353 points · 205 comments · srean
hunch.net
Top #1 · Best #13
Original article · HN discussion
Article
In 2023 after the ChatGPT release, it was clear to me that research needed to be more organized to succeed than was typical within Microsoft Research. The amount of support and focus which other research groups were applying was great enough that even with a clever idea pursued by one person it was likely to arrive late and unconvincing because one person could not move fast enough and the baselines which one person could assemble just were not strong enough to really show that an idea was worth taking flight. Several other folks thought similarly and we organized to create the AI Frontiers sub-organization within MSR.
In AI Frontiers, we actively tried to organize coherent research efforts. This was not precisely “top down” or “bottom up”, but rather mostly somewhere in the messy middle. There were disagreements of course, and resolving them was sometimes quite challenging. Compute availability was also an often-severe bottleneck. But at a high level I was under the general impression that the organization was succeeding in doing pioneering things, particularly given the small size of AIF (~50 people) and relative to what we could do previously. Much of the work of AIF was figuring out how to make agents work, for example the Autogen orchestration framework and the Fara computer use agent. In NYC however, several of us were interested in developing new fundamental capabilities such as the Next Latent objective which enables extrapolation, Dion3 which creates an optimized/improved Muon, or the Full Bandwidth Transformer which efficiently makes models function substantially more powerfully via recursion.
We also actively tried to share with the rest of MSR. For example, AIF decided to develop a monorepo that was shared by default with all of Microsoft Research. In this monorepo for example was the proven-capable edge scale pretraining codebase I talked about in the COLM keynote last month. This might seem like a minor detail, but the amount effort required to create a well-formed model creation pipeline is substantial and I’m aware of at least 4 efforts (the other 3 not in public-within-MSR repos) trying to develop model building pipelines.
In early September we were reorged into Microsoft AI. On the surface this could make sense, because putting two different AI organizations together creates opportunities for better concentration of effort, and there were places where AIF was ahead of MAI and of course vice-versa (MAI is much larger). In practice, there are substantial issues because the philosophy of the ex-Inflection leadership of MAI is incompatible. The core philosophy there is scaling, and aggressively not research. This might shock some folks who naturally think that the way you make better models is via research but there is plenty of evidence that bigger models are better models as far as the quality of the predictions they make and from a business perspective returns to scale are far more predictable than returns to research. In a scaling-only environment of course the primary effort is on getting/making/refining data, which is quite a step away from what we were working on. Aside from the incompatible focus, there was plenty of evidence that they just did not really want us.
It’s a tough situation to find yourself in. I consider the scaling-only focus to be both misdirected and not fun. It is an understandable failure mode—scaling is straightforward and it’s common for people to give up on a tradeoff between multiple competing ideals (like innovation and size) by short-sightedly adopting one in totality and dropping the other. But returns to research are real and significant. For example, the Bytedance experiments suggest a variant of the Full Bandwidth Transformer might be comparable to a model of twice the size, implying significant savings in training and inference for the same capability. Do the math—how much is it worth to halve training and inference cost given that the industry has investments approaching a trillion dollars?
So I situated my folks as best I could and left. I am quite fortunate in that there are many other people in the world who are capable of seeing the value of research and innovation which is my intrinsic center of interest. Every other founding AIF leadership team member seems to have come to a similar conclusion.
This does leave a question: Why not go back to MSR? I chatted with folks a bit but could not get away from two serious obstacles. The first is that I am just not comfortable being at a company where the research I do has no path to real use. I could not get innovation into use (or even seriously considered) when I was in MAI, so the prospects for success from MSR seem quite small. The second is that I’m afraid there’s a breakdown of the basic deal in MSR: do good work and good things happen. As far as I can tell we did good work and were non-consensually reorged away. Unfortunately, I would not be surprised to see that kind of thing continue to happen until MSR leadership develops a will to effectively organize to meet the moment.
So AI Frontiers is over. I’m sorry to say that there will not be internships with the folks there in the coming year—I enjoyed working with interns on many occasions. And my best wishes for the folks I leave behind. It is not hard to imagine a Microsoft of the future which becomes attractive for research again if the people in control can develop a little bit more wisdom.

The tempest prognosticator, also known as the leech barometer, is a 19th-century invention by George Merryweather in which leeches are used in a barometer. The twelve leeches are kept in small bottles inside the device; when they become agitated by an approaching storm, they attempt to climb out of the bottles and trigger a small hammer which strikes a bell. The likelihood of a storm is indicated by the number of times the bell is struck.
Dr. Merryweather, honorary curator of the Whitby Literary and Philosophical Society's Museum, detailed the sensitivity that medicinal leeches displayed in reaction to electrical conditions in the atmosphere. He was inspired by two lines from Edward Jenner's poem Signs of Rain: "The leech disturbed is newly risen; Quite to the summit of his prison."[1] Merryweather spent much of 1850 developing his ideas and came up with six designs for what he originally referred to as "An Atmospheric Electromagnetic Telegraph, conducted by Animal Instinct." These ranged from a cheap version, which he envisaged would be used by the government and the shipping industries, to a more expensive design. The expensive design, which took inspiration from the architecture of Indian temples, was made by local craftsmen and shown in the 1851 Great Exhibition at The Crystal Palace in London.[2]
On 27 February 1851, he gave a nearly three-hour essay to members of the Philosophical Society entitled "Essay explanatory of the Tempest Prognosticator in the building of the Great Exhibition for the Works of Industry of All Nations."[2]
The tempest prognosticator comprises twelve pint bottles in a circle around and beneath a large bell. Atop the glasses are small metal tubes which contain a piece of whalebone and a wire connecting them to small hammers positioned to strike the bell. In his essay Merryweather described the workings of the device:
After having arranged this mouse trap contrivance, into each bottle was poured rain water, to the height of an inch and a half; and a leech placed in every bottle, which was to be its future residence; and when influenced by the electromagnetic state of the atmosphere a number of leeches ascended into the tubes; in doing which they dislodged the whalebone and caused the bell to ring.
The leech would have difficulty entering the metal tubes but would endeavour to do so if sufficiently motivated by the likelihood of bad weather.[1] By ringing the bell it would signify that that individual leech is indicating that a storm is approaching. Merryweather referred to the leeches as his "jury of philosophical councilors"[1] and that the more of them that rang the bell the more likely that a storm would occur.
In his essay Merryweather also noted other features of the design, including the fact that the leeches were placed in glass bottles placed in a circle to prevent them from feeling "the affliction of solitary confinement".[1][2]
Merryweather spent all of 1850 testing the device, sending a letter to the president of the Philosophical Society and the Whitby Institute, Henry Belcher, to warn him of an impending storm.[1][2] The results of 28 of these predictions are kept in the library of Whitby Museum.[3] Merryweather stated in his essay the great success that he had had with the device.
Merryweather lobbied for the government to make use of his design around the British coastline but they instead opted for Robert FitzRoy's storm glass.[2]
The original device has been lost, but at least three replicas have been made. The hundredth anniversary of the invention brought renewed interest as a replica was made for the 1951 Festival of Britain. This non-working version was made from the description in a printed copy of Merryweather's essay and a copperplate drawing of the original. The device was shown in the Dome of Discovery and given to the Whitby Philosophical Society when the festival ended. This replica is still on display at Whitby Museum. Plans and photographs of this replica were then used to create faithful working models, one of which is on display at the UK National Meteorological Library and Archive at the Met Office in Exeter, Devon,[4] and another at the Great Dickens Christmas Fair in San Francisco.[2][failed verification]

Libghostty 1.0
libghostty-vt 1.0 is here. libghostty is a
portable, high-performance C library for terminal emulation, extracted
directly from the core of Ghostty. The 1.0 release means both the library
itself and the C ABI are now stable.
A little over a year ago, I wrote that libghostty is coming. At the time, the Zig module had just been merged, the C API didn't exist, and nobody but Ghostty was a consumer. Today, the C API is a complete terminal emulator, it runs in production for millions of people across hundreds of products, both free and commercial, and it has a real, enforced ABI stability policy.
This post is about how we got here and what 1.0 actually means.1
Who Is Already Using It
Since starting the Ghostty project in 2022, the most common question I've been asked is "why?". I already answered this in the libghostty is coming post, so feel free to read that if you wish. Today, I'd rather answer this by showing the broad industry impact libghostty has already had. I believe this strongly validates its existence.
A year ago, I used a bug in JediTerm, the terminal emulator in JetBrains IDEs, as an example of why terminal emulation is hard to get right. A year later, the terminal in JetBrains IDEs now runs on libghostty. Every IntelliJ, PyCharm, GoLand, etc. user now has a libghostty-powered terminal. Based on a report by JetBrains, that's over 12.5 million active users.
Neovim has an approved pull request
replacing libvterm with libghostty-vt. Among other things, it closes a
10-year-old issue
about reflowing scrollback on resize. The maintainers are waiting on a
tagged release before merging so that distributions can package the
dependency separately, and the release today should enable that.
KDE developers are experimenting with a Konsole replacement built on it. Vercel's Turborepo uses it to render task output in its TUI. devenv uses it to drive shells. Antithesis used it to fuzz TUI programs and found real bugs in btop and others. Ghostel brings it to Emacs. ghostty-web is the WASM build with an Xterm.js-compatible API. Commercial products like OrbStack embed it. And a whole wave of new terminals and "agentic" coding tools, such as herdr and cmux, have been built on it rather than writing yet another emulator.
There are community bindings for Rust, Go, JavaScript, Swift, Python, .NET, Elixir, Dart, Java, and more, and the awesome-libghostty list tracks well over a hundred projects.
More people today use a terminal powered by libghostty than use Ghostty the application, by a very large multiple. And libghostty is having a much larger impact than being "just" a terminal emulator.2
ABI Stability
1.0 means libghostty-vt follows semantic versioning and has strict
ABI compatibility
promises so that packagers across distributions and operating systems
can be confident packaging libghostty-vt and program developers can be
confident dynamically linking against it.
Beyond providing useful features, I believe the hallmark of a high-quality and enduring C library is ABI stability. So from the start, I took inspiration from C libraries I enjoyed working with and designed the API to have a strong, stable ABI that allows for future additions.
Every object is an opaque handle. The hundreds of values you might read or
write go through a small set of enum-keyed getters and setters, so we
can add new values easily without introducing a new symbol. Programs with
newer headers linked against an older libghostty get GHOSTTY_UNSUPPORTED
results instead of crashes or undefined behavior. The few non-opaque structs
we have carry their size so that fields can be appended later, or contain
reserved padding. Enums are pinned to int on every compiler, as much as
the C standard allows.
Our CI enforces our ABI policy. Every change is checked with libabigail against a committed baseline on Linux, and against golden type manifests on macOS and WebAssembly.
On ELF platforms, every exported symbol is also versioned, so the dynamic loader refuses to load a mismatched library by name rather than failing in some mysterious way later.
Packaging
In addition to ABI stability, the 1.0 release brings along the proper
build tooling, tarballs, dependency licensing manifests, documentation,
and more to enable every major operating system and distribution to
package libghostty-vt through standard official tooling.
Libghostty has its own release cycle, separate from Ghostty the application. And it has its own tarballs with only the files and dependencies libghostty needs, resulting in smaller sizes and simpler licensing verification and compatibility.
Each release publishes a signed source tarball along with a companion
dependencies tarball containing every Zig package in Zig's own cache
layout, so a distribution can build the library completely offline. The
build installs the shared and static libraries with a proper SONAME,
headers, pkg-config files, and a CMake package config, and it honors
--prefix, DESTDIR, and lib64. Debug info is kept by default so
distros can split it out. All of this is documented in
PACKAGING-LIBGHOSTTY.md,
which ships with the tarball.
Dependencies and Licensing
libghostty-vt is MIT licensed. At runtime it needs nothing beyond
libc, and it can be built fully freestanding if you don't want that
either.3
The library compiles in a small number of permissively licensed dependencies: simdutf and Google Highway for SIMD, a compact Unicode table for grapheme data, and Wuffs for image decoding in the Kitty graphics protocol. Both simdutf and Highway are built without libc++, so there is no C++ standard library dependency.
There is no copyleft code anywhere in the dependency tree. Every dependency is listed in a machine-readable manifest with its version, SPDX license, and hash, specifically so distros can fill in their bundled-library metadata more easily.
If a distro would rather dynamically link the system simdutf or Highway, there's a build flag for that.
Portability
libghostty-vt is highly portable. The table below lists all the platforms
and architectures that we build and test (full unit tests plus running all
examples) in CI:
| Platform | Architectures |
|---|---|
| Linux (glibc, musl) | x86_64, aarch64 |
| macOS 13+ | x86_64, aarch64 |
| iOS 13+ | aarch64 |
| FreeBSD | x86_64, aarch64 |
| Windows | x86_64 |
| Android | aarch64, x86_64, arm |
| WebAssembly | wasm32 (freestanding) |
There is a second set of platforms we build in CI but do not run tests for. These systems all have known users; we just haven't set up the machinery for automated testing:
| Platform | Architectures |
|---|---|
| Bare metal | riscv32, thumb |
| WebAssembly (WASI) | wasm32 |
| Windows | arm64 |
| illumos | x86_64 |
| 32-bit x86 | x86 |
Each of the tested platforms gets the artifacts it expects:
- Linux and FreeBSD get a shared library with a proper SONAME and versioned symbols, a static library, headers, pkg-config files, and a CMake package config.
- macOS and iOS get a dylib with an @rpath install name and
compatibility version, plus an XCFramework covering macOS, iOS, and
the iOS simulator that drops straight into Xcode or Swift Package
Manager.
- Windows gets a DLL with a .pdb, an import library, and a static
library. The library is built with the GNU ABI, but MSVC programs
link against it through the import library and CI verifies this.
- Android gets a shared library built against the NDK with 16 KB page size support, as required by Android 15+.
- WebAssembly ships in two flavors, one optimized for speed and one
for size, and the small one is under a megabyte with every feature
enabled. If you only need a read-only viewer, subsystems like input
encoding, search, selection, and Kitty graphics can be compiled out
with a build flag, which roughly halves the module. Every function
stays exported and simply returns GHOSTTY_UNSUPPORTED so your code
doesn't have to change.4
Portability isn't just about the ability to build and run. It's also about resource usage and being able to work in a wide variety of resource environments.
For resource usage, the library creates no threads, allocates only through
an allocator you can customize, and uses minimal compute and memory.
I've run 10,000 active terminals, each with a live shell producing output,
on a Linux server with 4 cores and 8 GB of RAM. In this test, I had to use
dash because bash used far more RAM than libghostty-vt and wouldn't fit
into the 8 GB budget.
What's Next
Libghostty 1.0 is a major milestone.
You can now create a terminal in ~1,500 lines of C that has more features and better performance than just about any terminal that existed in 2025, and most today in 2026.5 And thanks to the rich ecosystem of language bindings, you can do this in every major programming language. You get this for free. For almost no effort. You can just do it.
libghostty-vt is a generalized library, so we will focus on stability
while implementing as many terminal protocols as exist
(giving options to enable/disable them, of course) so that embedders
have the luxury of choice.
Every bug any libghostty-vt embedder reports makes everyone else in
the ecosystem better. Every feature we ship in libghostty-vt becomes
available to everyone quickly and safely. Terminals can move faster with
less fragmentation.
Thank you to everyone who contributed to the library, wrote bindings, filed bugs, and shipped something on top of it while the API was still experimental. As with all open source, this was the work of a large community.
Docs, examples, and downloads are at lib.ghostty.org.
Boo. 👻

A learning app you run yourself, on a Raspberry Pi, for the people at home.
skrongle.ad.mov
Skrongle is one small binary that teaches from courses made of JSON files: lessons, adaptive quizzes, five-minute practice sessions, games, flashcards and an AI tutor. Spanish and French courses ship with it; any subject that fits units → lesson groups → lessons can be a course, written by hand, uploaded from files, or described to an AI that writes it for you.
It is built for a handful of people who know whoever runs it: a family, a class, a few friends. Up to eight accounts, no e-mail, no outside service of any kind except the AI providers you choose to give it a key for. A Raspberry Pi Zero 2 W runs it with room to spare.
For the step-by-step path, follow the home Wi-Fi guide, written for someone who has never run a server, and the Tailscale guide to reach it away from home. The technical reference is docs/self-hosting.md. The short form:
- Download the release
tarball for your machine: skrongle-<version>-aarch64.tar.gz for a Pi
(64-bit Raspberry Pi OS) or -x86_64 for a PC running Linux.
- Unpack it, install the systemd unit it contains and start the service. The server writes an owner link to its log: open it to make the first account, which is the owner's.
- Everyone else joins with an invitation link the owner makes on the Manage Users page.
- Optional: paste an AI provider's API key on the same page. It serves every account, and the owner can hide the AI features for everyone with one switch.

| Accounts | Up to 8, each with up to 4 signed-in devices |
| Who signs up | Only people the owner invites (the default, SKRONGLE_SIGNUP=invite) |
| | None. Every link is shown on the page instead of sent |
| Password reset | The owner sets a temporary password from the Manage Users page or the command line |
| Second factor | An authenticator app, per account |
| AI | Your own keys: Anthropic, OpenAI, Google, DeepSeek, Mistral, xAI, OpenRouter, or an Ollama-compatible server on your network |

| Memory | about 16 MB idle, about 21 MB in use; the unit caps it at 48 MB |

The limits that keep it there are in src/caps.rs: 8 accounts, 4 sessions
each, 32 open connections, 2 tutor replies at once, one course generation at
a time, and a course cache bounded by the account count. All state lives in
SQLite, so the process has no growth path.
- Passwords: argon2id with a per-user salt; unknown addresses verify against a dummy hash so login timing does not reveal whether an account exists.
- Sessions: 256-bit random tokens, 30-day TTL, deleted on logout, purged
hourly; HttpOnly; SameSite=Lax cookie, Secure behind TLS; at most four
per account.
- Every state-changing request passes a same-origin check; the JSON API only
accepts Content-Type: application/json.
- Course files are validated on every save (1 MiB per file, 400 per course). Lesson Markdown passes raw HTML through, so only load courses you trust.
- API keys are saved encrypted at rest (ChaCha20-Poly1305 under
SKRONGLE_SECRET_KEY or <db>.key) and never shown again; only owners see
the page that holds them.
- The person running it secures the login: a strong password per account, an authenticator app, and the server reachable only over Tailscale or a VPN, never through a forwarded port.
