Preamble
I've always had a fascination with reverse-engineering browser fingerprinting scripts. Most of my time has been spent looking at the usual suspects (popular fingerprinting libraries like FingerprintJS and more sophisticated scripts used by anti-bots like Cloudflare Turnstile, Akamai, and others).
At some point, I wanted to know what else was out there. I had an idea: What if I crawled the web and intercepted fingerprinting-related browser API calls and mapped it all?
To do this, I used the Tranco Top Sites list and began crawling using Playwright. I would hook canvas toDataURL calls and common fingerprinting/anti-bot properties like navigator.webdriver to filter out benign canvases.
For those unfamiliar, canvas fingerprinting generally involves drawing text, shapes, or other graphics onto an HTML <canvas> and extracting the resulting pixel data. Subtle differences in how browsers, operating systems, graphics drivers, and hardware render those graphics can help distinguish one browser environment from another.

Background
Control Monitoring is a powerful method for ensuring the alignment and safety of autonomous agents. Since the Hugging Face Incident, the need for control monitoring on top of existing safety mechanisms was reinforced: OpenAI started investing more heavily into monitoring safety tools. This includes asynchronous control monitoring to flag misalignment during runtime, where asynchronous monitors detect potentially high-severity issues, and surface or pause the session. Another common use case is chain of thought monitoring during RL to audit the model’s alignment.
The drawback of asynchronous monitoring methods is that harmful actions are already executed by the time they are flagged. This is expensive: when destructive actions or actions leading to information leakage occur, these harmful actions can cause irreversible damage. In cases of credential exposure, leaked credentials need to be rotated and third-parties need to be notified.
Our monitoring approach goes a step further: our monitoring model runs as a sidecar and prevents harmful actions in real time, before they are executed. The sidecar ingests part of the trace as context and prevents misalignment and harm synchronously (instead of flagging in post). Our approach additionally steers agents once harm is detected, enabling a safer and more widespread deployment of autonomous agents, and allows us to scale model capability faster.
This article shows how our monitoring approach works.
Why Context is important
Conventional safeguards (e.g. classifiers or probes) don’t include context: each action is judged in isolation, missing the context and failing to detect harm that spreads across multiple steps.
For example: production logs stored in the variable LOG contain a database password.
An agent attempting to create a GitHub issue referencing $LOG exposes the database
password. It is structurally impossible for a conventional safeguard to detect that posting
$LOG to GitHub is harmful, because it lacks the context that the LOG
variable contains a database password.
Even a perfect classifier (or a human) cannot prevent harmful actions spread over multiple steps without the necessary context.
Control monitors ingest the trace as context. The context consists of parts of the
execution trace. Seeing the context allows control monitors to combine information from previous
steps into its verdicts. In this example, the control monitor recognizes that LOG
contains a database password and that executing a tool call posting $LOG to GitHub
would leak the credential. With this context, a control monitor correctly denies the action.
Monitor Capabilities
The control monitoring model runs as a sidecar alongside the agent, streams the trace to the monitoring model, and prevents harmful actions in real time (including harms spread over multiple steps).
Its work is split into two phases: context accumulation (expensive, asynchronous); and tool call classification (cheap, synchronous).
Context accumulation: during the agent’s execution, the monitor asynchronously accumulates the agent trace into its context. The trace is continuously streamed from the agent’s harness to the monitor model.
Tool call classification: tool calls are then classified in blocking mode, in the critical path of the agent. Before each tool call is executed, the monitor model is sampled for a classification. The context during classification consists of all accumulated past turns, and allows the monitor model to detect highly contextual harms, including harms spread over multiple steps.
Classification is sub-100ms (regardless of execution length). Because the expensive context accumulation happens ahead of time, while the agent is still running, almost all the compute is already done by the time a tool call classification is performed. Combined with a thoroughly optimized inference stack, we are able to serve a high-parameter monitoring model in real-time at sub-100ms latency per tool call.
The following demo shows the monitoring model in different scenarios. The agent trace is generated at 30 tok/s and is streaming to the monitor model on the right. The monitor model is a high-parameter model running in real time; its latencies are displayed for each event.
Supporting Long Executions, Multi-Agent workflows, and Robustness
The model supports monitoring agents with unbounded length with manageable context loss while being robust to external harms (e.g. prompt injection).
Since the monitor model is able to ingest context of unbounded length with manageable context loss, there is no limit on the execution length. In multi-agent workflows, execution streams can be joined and jointly monitored.
The mechanisms supporting monitoring of unbounded execution lengths ensure that latencies do not grow with execution length. The mechanisms are done entirely asynchronously during context accumulation, and have no impact on the tool call classification latency and do not cause interruptions.
Lastly, depending on the configuration, parts of the execution trace are ingested that are relevant to detecting misalignment and harmful actions. This makes the model robust to external harms (e.g. indirect prompt injection).
Control evaluations
As a safety tool, the monitor model is able to prevent harms caused by attacks that already broke through frontier model defenses.
We measured the effect of the monitor on the attack success rate (ASR) on the DecodingTrust red-teaming framework. A lower ASR means that the monitor model prevented attacks in addition to what frontier built-in safety alignment and safeguards missed.
Using the monitor model as a safety tool cuts ASRs by roughly an order of magnitude across agents and domains, indicating that this approach provides additional safety on top of safety alignment and built-in safeguards.
The false positive rate on benign agent executions was measured at 0.048% per action. In production, false positives are recoverable, since denials do not interrupt agent execution; the agent is steered and is able to continue its execution. The cost of false predictions shows up as execution overhead: falsely denied actions add extra steps and compute to the agent’s execution.
Latency evaluations
The model is fast enough to run as a sidecar in real time, in blocking mode for tool call classification. The latency is upper-bounded at 100ms due to the mechanisms supporting long executions, even for executions with unbounded length.
Evaluated on SWE-bench Lite (Claude 3.5 Sonnet), using the monitor adds 0.2–0.6% of end-to-end task time on the OpenHands runtime.

Ghostty now supports Kitty graphics animation and relative placements. These were the last major features of the Kitty graphics protocol that Ghostty didn't support.

Ghostty now transparently compresses scrollback that isn't visible, reducing the physical memory those pages use by 70% to 90% for typical text-heavy history. Compression only runs while the terminal is idle and pages are decompressed on demand when you scroll back or search, so it has no measurable impact on I/O throughput.
Thanks to compression, the default scrollback limit has been raised from 10 MB to 50 MB per terminal. On platforms that support compression, a full scrollback still generally uses less physical memory than the old 10 MB limit did.
Note
Compression lowers resident (physical) memory, not virtual memory, so look at resident memory when measuring it. It is currently available on macOS and 64-bit Linux.
Beyond scrollback, memory usage is lower in many places:
- A new, empty terminal now uses about 16 KiB of terminal page memory on macOS, down from 128 KiB in Ghostty 1.3.1.
- On macOS and Linux, memory freed by clearing or trimming scrollback is now returned to the OS instead of being held until the terminal closes.
- Hidden tabs release their GPU resources. On macOS, with one visible tab and 20 hidden tabs, GPU memory dropped from about 385 MiB to 18 MiB. Rebuilding them when a tab becomes visible again takes under a millisecond.

There are performance improvements across the board in Ghostty 1.4 that yield significant gains compared to prior Ghostty versions.
The biggest win came from a surprising discovery: on macOS, the kernel caps every read from a pty at about 1 KiB no matter how large the read buffer is. Previously, Ghostty processed each read as it arrived, so per-read overhead was paid every kilobyte, and the program writing output sat blocked while we parsed. Ghostty now drains the pty on one thread while parsing on another, raising end-to-end I/O throughput by 25% to 55% on macOS (M4 Max, plain and Unicode text) over Ghostty 1.3.x.
VT processing itself is also much faster. In parser benchmarks, plain
ASCII text went from 128 MB/s to 725 MB/s (5.7x), CJK text got 3.4x
faster, and a 2.6 GB dataset of real-world terminal recordings
from asciinema is processed about 25% faster.
Together, these changes took cat-ing a 150 MB text file on macOS from
1.5 seconds to 566 milliseconds.
Other notable improvements:
- Resize: resizing a terminal with a large scrollback is about 6x faster (120x80 with 10,000 lines of scrollback), and 3x to 5x faster with history full of CJK text or emoji.
- Rendering: the renderer holds the terminal lock 2.7x to 11x less per frame, leaving more time for the I/O thread during heavy output.
- Copy and search: formatting terminal contents as plain text, HTML,
or VT, which backs clipboard copy, write_screen_file, and scrollback
search, is 1.5x to 8x faster.
- Launch (macOS): about 15% faster from launch to visible window, and 27% faster to the first rendered frame.
- Idle energy: on macOS, the renderer's display link now sleeps when there's nothing to draw. On GTK, hidden tabs stop rendering, matching macOS.
- Large OSC sequences: OSC 52 clipboard payloads parse about 30x faster, and even short sequences like title changes are about 6x faster.
The GTK app has a new rendering pipeline. It no longer uses GtkGLArea.
Instead, the renderer draws with EGL on its own thread, exports each frame
as a DMABUF, and hands it to GTK to display. Rendering is now
triple-buffered, which should greatly reduce tearing, and no OpenGL calls
run on the main thread anymore, which let us remove a number of
workarounds.
The most visible result is crisp text under fractional scaling. Text and box-drawing characters are no longer blurry with fractional display scaling such as 125% or 150% (#1938 ). We fixed this once before, but it came back after upstream GTK changes. Ghostty now renders at the window's true fractional scale, so every rendered pixel maps to exactly one pixel on screen.
The new render surface needs a system EGL library (see Changes for Package Maintainers). On GPU drivers that can't export DMABUFs, Ghostty falls back to copying frames through the CPU, which is slower but works.

Ghostty now implements the Kitty clipboard protocol (OSC 5522) on both macOS and GTK. Ghostty 1.3 could parse the protocol but didn't implement it.
OSC 52 can only read and write plain text. The Kitty clipboard protocol lets programs running in the terminal read and write any kind of clipboard data, such as images or HTML, and lets them pick among the formats on the clipboard. Programs can also enable paste events (mode 5522), which tell the program what formats a paste contains so it can read the one it wants. This is how a terminal program can accept a pasted image, for example.
Clipboard access follows the existing clipboard-read and
clipboard-write configurations. By default, reads prompt for permission
and writes are allowed. The permission prompt shows a preview of the
clipboard contents, including images. Programs that send a password can
have your answer remembered for the rest of that terminal session. A new
clipboard-write-limit-bytes configuration limits the size of a single
write (default 64 MiB). A write over the limit fails and leaves the
clipboard untouched.
You can now rearrange splits on GTK by dragging them, matching the macOS feature introduced in Ghostty 1.3. When a tab has two or more splits, each split shows a drag handle at the top. Grab the handle and drop the split onto any other split, including splits in other tabs and windows. An overlay shows which side of the target split it will land on. The terminal contents, working directory, and running processes all move with it.
A new drag-handle configuration controls when drag handles are shown on
both macOS and GTK: auto (default), always, or never. With never,
splits can't be rearranged with the mouse. Hiding the handles was a
common request from users who found them in the way.
On GTK, splits can only be dropped onto other splits. Dragging a split out to create a new tab or window is macOS-only.

Ghostty 1.2 introduced SSH shell integration features
as a work in progress. In Ghostty 1.4, they're backed by a new
ghostty +ssh CLI action: a drop-in ssh wrapper that prepares the
remote session for Ghostty and then runs the real ssh with your
arguments forwarded unchanged.
ghostty +ssh user@example.com
# Or alias it so every ssh invocation goes through it
alias ssh='ghostty +ssh --'
Before connecting, +ssh installs Ghostty's terminfo on the remote host
so the proper xterm-ghostty TERM value can be used, and forwards
COLORTERM, TERM_PROGRAM, and TERM_PROGRAM_VERSION. If the terminfo
install fails (for example, tic isn't available on the remote), it falls

--forward-env=false, and --verbose control each step.
The ssh-env and ssh-terminfo shell integration features (still opt-in)
now call +ssh too. Previously, each shell integration carried its own copy
of this logic, which made up roughly a third of our shell integration
scripts. Now bash, zsh, fish, elvish, and Nushell all behave identically,
and you can get the same behavior from scripts or anywhere else by calling
ghostty +ssh directly.
The terminfo install itself is also more reliable. Ghostty now always
installs its own bundled terminfo rather than accepting whatever
xterm-ghostty entry the remote already has, and it reinstalls
automatically when a Ghostty update changes the terminfo. It also no longer
needs infocmp or Ghostty's terminfo on the local machine. Installs are
cached per host and port, so two machines behind one address no longer
share a cache entry. And ssh-env no longer silently overrides SetEnv
entries in your ~/.ssh/config (#11518 ).

destinations (ghostty +ssh-cache user@example.com) and has a new
--prune=30d flag. See the breaking changes if you

Syrinx: A censorship-resistant communications platform
The idea of Syrinx was born many years ago when I started wondering if it would be possible to build a system that couldn't be censored. What if you could come back up as quickly as you can spin up a new server, in the case of a hostile take over? Turns out that by having your data cryptographically signed and distributed among the network members you don't have to worry about backups any more.
This idea became even more relevant in the last year or so when the latest (and the most consequential) attack on our privacy began spreading through different countries in the form of age verification laws.
The State of Online Privacy
Online rights have been slowly stripped away, but to be fair they haven't been taken away as much as we have given them up in exchange for convenience. We provide constantly our location, every message we send, every photo we take, every email we write, every song we listen, every article we read, every video we watch. All of our information is constantly harvested, processed, analyzed, and sold. Sometimes they want to sell us stuff, sometimes they want to know our immigration status, sometimes they want to know our political affiliation. We have no control over any of this.
And now that they have all that information we would be forced to attach an ID card to it, to make sure that you can't escape the panopticon.
The 57005 Internet?
I'm sure you've heard about the 57005 Internet theory, which states that most of the Internet traffic is just bots talking to each other. Now exacerbated by most content being AI-generated. I don't know if this is true, but I don't care really, because google is not the Internet, instagram is not the Internet, twitter is not the Internet, and reddit is not the Internet.
The Internet is decentralized by design. The fact that most of the traffic is handled by a handful of corporations is an anomaly, this is not how it was supposed to work.
The Proof of Concept
Syrinx is an experiment, a PoC. I wanted to see if I was able to come up with a communications platform that:
- Was private.
- Could survive a takedown.
-
Was easy to run.
- And performed reasonably well in modest hardware.
- Could federate with other communities.
- Gave admins certain tools of moderation.
The application stores all data in the devices of its members, the server meanwhile acts as a torrent tracker, i.e. it knows "who has what" but it doesn't know what the content is. So if I want post X it knows who has it, not what it's written there. A client encrypts the content, sends it to the server, which in turn delivers it to the user who requested it. The content gets decrypted, validated, and stored.
I was hesitant to call Syrinx "P2P" so in the documentation I called it P2P-ish. This is because establishing direct connections between peers across NAT'ted routers is extremely unreliable, so the server acts as a relay in between the peers.
Since the database is distributed among the peers a hostile take-over of the server does not yield any useful information besides usernames (emails and bios are optional.) This allows the system to become operational again quickly as long as users export their data from the old app and import it into the new system.
Moderation is important for a community to make sure that communication remains safe, respectful, and overall aligned with the community-established guidelines. This power given to a few people is balanced by publishing every action they take to a cryptographically-signed public ledger that every member can read. That makes them accountable and unable to exercise power in darkness.
This goes hand-in-hand with the community being invite-only. That instills a sense of responsibility on the members when inviting other people, knowing that their actions reflect on you as well, and bringing in members that could disrupt the peace could have consequences on your own account.
Just because I don't agree with what you say does not mean that you don't have the right to say it. Members who disagree on how the community is run could easily start their own. That's why it's important that the software is easy to run at home, in whatever piece of hardware you have lying around. This allows for small communities to flourish that can then federate with each other in a sort of mesh.
A Message to You, Rudy
This is my message to the hacker community out there: We have the means to reclaim the Internet. We don't need to depend on corporations for hosting or compute power, that's not how the Internet was designed. In fact, the hyper-centralized Internet that we have today is an anomaly.
As I always say, Software Engineering is the art of managing trade-offs, and Syrinx is no exception. There are big trade-offs when it comes to decentralized services. Yet, I believe that rather than losing something, these limitations give the system very particular and unique traits that I have come to appreciate.
Let me go into each trade-off one by one and explain how they, in my opinion, improve the user experience.
Content-Type: text/plain
Syrinx is text-only and posts limited to 140 characters. This is not because it's impossible to have P2P multimedia, but because solving it for text was big enough of a problem to tackle in a PoC. On top of that my phone for example reports that the app is provided with a quota of 10G of storage even if I don't have 10G phisically available in my device. On the client we have to be very conservative when it comes to storage, developers should consume it carefully and responsibly.
That said, this system is inspired by the golden days of Twitter, when 140 characters, far from limiting expresssion, fostered creativity. I would call this decision "partly technical, but mostly intentional", since I could have started with a much bigger limit with no noticeable impact on storage. Just to give you an idea, 90% of a post's size is consumed by its envelope, namely the cryptographic signatures.
Text-only means that no profile pictures are allowed either. I have discovered that this has some very interesting security properties. Since the username is just free text you could try to impersonate a user by using similar-looking characters or maybe even invisible characters. However, since you can't have an arbitrary profile picture (your avatar will be auto-generated from the server-generated user ID, AKA an identicon) you will get a distinct avatar, giving both accounts unique visual characteristics that prevent impersonation.
Content Travels at Angular Speed
As we already established the server does not hold any content, therefore peers have to be online to deliver it; if there's nobody online at the time you request the content, you can't access it. This is inspired by the BBS of the early days of the Internet, in which a message could take days to reach the recipient because servers would only sync once a day, at night.
In Syrinx this means that a user you follow who is located on your antipode (i.e. on the exact opposite side of earth) may be sleeping when you try to access it. In order for you to get it they should deliver it to someone that's closer to your timezone while they are awake, and then that user could act as your provider.
I really love this concept that delivery not only doesn't have to be immediate, but that content could literally take hours or even days travelling across the earth before it can reach you.
The Walled Web
I said earlier that we have all the tools to reclaim the Internet. And I do believe that. However, the entrypoints are very well policed.
There are just a handful of browsers available and all of them, directly or indirectly, controlled by corporations. The view is even more dire in the mobile world, where the whole ecosystem is built and maintained by corporations. They decide who gets to play in a game where they not only set the rules, but also change them whenever they feel like.
Progressive Web Apps are a tiny crack in that wall, but with many limitations (with respect to native apps) many of them undocumented or disguised as bugs. It's not uncommon to hit features that are supposed to work according to the docs, but haven't for years. And the incentives for fixing them are not really there either.
Still, we can work with what we have. For now I've decided to leave certain features out, such as notifications. I want the user to come to the app when they decide, not the app to scream for attention. I do see the value in getting notified of important events, but what "important" means should be defined by the user.
Data Migration
This is the one problem I have not been able to solve yet. In a centralized environment you would have a domain acting as the server's identity. If I query that domain I can be reasonably certain that I'm reaching the actual service.
In a decentralized world there's no single authority to tell me who is who, I depend on someone (that I trust) giving me the public key of the server over a secure channel to be able to verify their identity. Now imagine that I want to migrate my user from one community to another.
If these 2 communities are federated (meaning that they have already verified each other's identities) the new home could validate that the data was signed by the old server and accept it. But what if they don't know about each other? How can I be sure that the user didn't craft a set of signatures themselves, pretending to be server signatures?
And what if the original community is permanently down? A user who doesn't want to lose their posts decides to migrate their identity to a new server. Now even if the user brings the old server's public key along there's no server to ask whether they even know about this user. If this user claims they they wrote a post in 2019 about a new pandemic coming up, shall we trust them? If you do, you (the server) are vouching for the post's validity.
It's all complicated enough already that we are moving just public posts between servers, now add private chats too in the mix. It's a mess. This is, in my opinion, the Achilles' heel of this solution, and one that I still have no satisfactory answer for. To be fair, no centralized, proprietary service allows you to migrate your data and nobody seems to have a problem with that (you can export it at best, but nobody will let you import it.)
So What's Next?
I don't know. I proved what I set out to prove: Whether it was possible to have a federated social network that could withstand censorship while providing a basic set of tools for moderation. And I'm very satisfied with the result. What happens next is up to the community.
Let me know if you find it useful, I would appreciate any kind of feedback.
