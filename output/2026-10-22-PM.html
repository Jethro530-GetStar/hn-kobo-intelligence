Article
PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35 fix two critical vulnerabilities that can allow unauthenticated remote code execution. All PHP users are strongly encouraged to update immediately.
Who is at risk: all PHP installations serving web requests, including PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP and LiteSpeed. We consider the risk highest for mod_php, with a demonstrated exploit where an unauthenticated request can trigger the attack before any application code runs.
The vulnerabilities:
- RCE via OOM corruption, CVE-2026-109618 (GHSA-w8hw-w9fx-j79w): out-of-memory handling can interrupt PHP while internal request data is only partially initialized. Request cleanup may then treat the invalid data as valid.
- RCE via stale global state, CVE-2026-109619 (GHSA-6wmf-4rv5-p3rp): request-owned internal state can survive after its backing memory has been freed. A later request handled by the same worker may use that stale state before normal initialization resets it.
How to update:
- Update to PHP 8.5.12, 8.4.27, 8.3.36 or 8.2.35. Source downloads are on our downloads page. Windows source and binaries are on the same page.
- Linux distributions and LTS vendors received the patches in advance, so check your vendor for updated packages.
- PHP 8.1 and older no longer receive updates from the PHP project. Some distributions and LTS vendors provide backported fixes, so contact your vendor for details, or upgrade to a supported version.
- If you rely on the volunteer-maintained rpms.remirepo.net, we urge you to switch to distribution packages or build from source, so you can immediately apply updates. The repo will not have updates today.
- Given the severity of these vulnerabilities, the PHP security team provided minimal source-backports for PHP 7.4, PHP 8.0, and PHP 8.1 to help people building from source or without access to an LTS vendor.
If you cannot update immediately: while only an update is a complete solution, the following measures reduce exposure to specific attack paths but do not make an installation safe.
RCE via OOM corruption (CVE-2026-109618):
- Set memory_limit=-1, preferably in a way applications can't override, such as php_admin_value in the FPM pool or Apache configuration, and check that no pool, directory or application setting puts a finite limit back. This removes the controllable PHP memory limit failure, but an underlying allocation failure can still reach the vulnerable path.
- Set a low post_max_size. For applications that don't require file uploads, set post_max_size = 8M. If file uploads are necessary, set post_max_size = 32M. Keep upload_max_filesize below post_max_size.
Consider enforcing limits at the web server or proxy level for decoded request size, input field count, multipart part count, header count, and nesting depth. These
limits must also cover requests without a usable Content-Length.
- Use a container or cgroup limit as an availability boundary, preferably with a policy that kills only the affected worker. Do not substitute RLIMIT_AS or RLIMIT_DATA, as these can cause the vulnerable allocation failure.
RCE via stale global state (CVE-2026-109619):
- Set session.upload_progress.enabled=0 and restart every worker. Use php.ini, an FPM pool or server
configuration that applies before request parsing. Do not rely on ini_set() or FPM .user.ini. This blocks the confirmed session paths but not other variants.
- On PHP 8.5, set fatal_error_backtraces=0 and restart every worker. This blocks the confirmed fatal backtrace path only.
- Remove invalid or deprecated settings applied per request that emit diagnostics before initialization. Hiding diagnostics with error_reporting, display_errors or @ does not help.
- Fix attacker-reachable fatal errors and execution timeouts, including failures in callbacks, upload or import processing and cleanup.
The advisories linked above have the full technical details.

42 skills that build, describe, ship and announce apps — to the App Store and Google Play, and outside them, on the Mac and on Windows. Each one loads only where it is wanted.
The story behind it — why one big instructions file stopped holding, and what replaced it: the article.
They are Claude Code plugins. You enable the tracks a repo needs, and a session opened there carries them; a session opened anywhere else does not.
Built for Claude Code, and tested only there. The scripts the skills run are
ordinary command-line tools any agent can call, but the loading — tracks, the
marketplace, enable.py — is Claude Code's plugin system, and most skills find their
scripts through ${CLAUDE_PLUGIN_ROOT}, which only Claude Code sets.
claude plugin marketplace add yybd/app-factory
cd ~/code/my-app && python3 ~/.claude/plugins/marketplaces/app-factory/factory/enable.py
# then the install lines it prints, and QUICKSTART for the rest
QUICKSTART.md walks the whole thing — fifteen minutes, one app, with a check after every step.
The usual way to steer a coding agent is one large instruction file. Everything goes in: release rules, test conventions, SEO, the way you name things. It does not hold. The file grows past what stays in view, rules contradict each other, and the agent proposes an Android deploy while you are editing a website.
The failure is not that the agent forgets. It is that everything was told to it at once, whether or not it applied.
So: nothing is global. A skill is a document the agent loads when its description matches what you asked for, and the descriptions are the only part that is always in context. What it costs to have 42 of them available is about 8,400 tokens of descriptions — and only in a repo where you turned them on.
Eight tracks of skills, plus one that does setup:

Each track's own README lists what is in it, what it costs, and what it needs installed. The counts above are generated from the skills on disk — in this repo, every number that can be counted is.
Executors do one thing: play-store-ship builds, signs and uploads an AAB.

Orchestrators sequence executors without doing their work. prepare-app-release

The division matters because the second kind is where a release goes wrong: not in any single step, but in the order, and in the step nobody remembered.
It writes files in the repo you point it at, reads credentials in place without ever copying or printing them, and uploads to the stores at the end of skills whose whole job that is. It never submits an app for review, never changes a price, and never pushes.
There is one directory it will delete from. TRUST.md is the full list, written to be read before you enable anything.
Nothing, to install. Individual skills need what they need — Xcode for Apple, a JDK for
Android, fastlane for either store — and each says so and stops rather than failing
halfway. COMPATIBILITY.md has the table.
You do not need a data repo, a website, or the companion guards project. All three are optional and the skills detect their absence rather than assuming it.

Once you are shipping more than one app, a second problem appears: an app's code, its
listing text and its website are different repos, and a session stands in exactly one of
them. Work left in another is not missing — it is invisible, which is how "done" gets
said over a clean git status.
That is RepoGuards: one registry that decides which tracks load where, and guards that refuse a write into a repo the session is not standing in. It is a separate marketplace, it is optional, and nothing here requires it.

5. AI Is 'Amplifying the Destruction' of War
FULL TEXT
1 points · 0 comments · gumby

Article
The UN met this week to discuss, among other things, the threat of autonomous weapons.
“The technology is developing at a pace that is very concerning,” Laurent Gisel, the head of the International Committee of the Red Cross’s (ICRC) legal warfare team, told 404 Media. Gisel was in NYC this week to address the UN about all the things that are driving conflict across the planet. His prepared remarks include a statement on the illegal arms trade, nuclear weapons, mines, and – of course – AI.
Autonomous weapons have been a hot topic at the UN this year. In September, the UN attempted to pass a treaty that would govern the use of killer AI weapons. Diplomats from Russia and the US stripped it of its power.
But the UN has pressed forward. On Tuesday, the international governing body announced a new initiative that would grapple with the issue. But, as Gisel said: “multilateral processes take quite some time” and “we already see the effects on the battlefield.”
AI is already picking targets and killing people. Gisel said the technology is “amplifying the destruction, amplifying the violation of the law, amplifying the humanitarian harm caused by conflicts.”
Israel used an AI powered by Microsoft to pick targets in Gaza. In Ukraine, AI-powered Russian drones are deciding which humans to kill. The United States military is pitching itself as an “AI-first” fighting force. Secretary of Defense Pete Hegseth recently announced Project Meridian, an initiative to guide the AI-powered autonomous weapons of the future. Three of Meridian's leads are Elon Musk, defense contractor Palmer Luckey, and Newt Gingrich.
For Gisel, one of the biggest dangers of AI is how fast it is. A core selling point for the tech is that it can help commanders make decisions faster. But that also accelerates the pace of mistakes. “Targets are created at higher speed and higher frequency, and are actually then prosecuted quicker, and with that give us great concerns in terms of the level of human control that is retained,” he said. “The human is supposed to remain in the loop.”
The human does not always remain in the loop. The Israel Defense Forces told journalists it did not thoroughly vet the kill lists generated by Lavender, the AI system it used to pick targets in Gaza. “It's known in the [civilian world] [...] that humans tend to trust the systems,” Gisel said. “That it's more the case when the humans are tired, when the humans are under stress, when the humans have to deliver quickly, and that's of course exactly the situation in which soldiers are in. So all of that gives us a lot of concerns in terms of retaining control on the use of force in armed conflict.”
AI boosters often pitch AI as an “easy button,” a way for people to brute force a complicated task and get it over with. But the consequences are much different when someone in Silicon Valley is parsing spreadsheets or reverse engineering code than when they’re prosecuting a war in the Middle East.
“That's something that the developers of those systems don't necessarily realize either, because some of those systems are developed by technological companies very far away from the battlefield, and they are not naturally all developed for battlefield use,” Gisel said.
International humanitarian law is an ever-evolving legal negotiation between world powers meant to limit the devastating effects of war. It’s imperfect and countries with vast armies like the US and Russia often do not abide by it. The ICRC, which Gisel represents, exists explicitly to shape these rules and laws. Some of the laws are old, far older than AI, but according to Gisel humanitarian law applies to “all weapons, means, and methods of warfare. Those of yesterday, those of today, and those of tomorrow.”
Beyond the opportunity to code humanitarian law into AI, Gisel said there should be new rules and regulations for the new technology. “Not to prohibit them all, but to prohibit specific categories of autonomous weapon systems and put specific restrictions on others,” he said.
"...Once the genie is out of the bottle, it's very, very much difficult to put it back in the bottle"
But he does have redlines. The first is any AI support system that removes a human being from the kill chain. “That requires specific limits and guardrails and restrictions from our perspective,” he said.
“The other type of autonomous weapon system that we recommend prohibiting is those that would target human beings directly, where the target profile is the human being, as opposed to a tank, weapon systems, or another typical military objective, and the reason why is based on ethical concerns, humanitarian concerns, and a moral line,” he added.
Autonomous weapons have existed for a long time. Some US warships have gatling guns that track and destroy incoming targets automatically. The difference is that those weapons track ships and missiles, not human beings.
According to Gisel, one problem with autonomous weapons that target humans or AI support systems that pick targets is that they’re unpredictable. He said banning unpredictable weapons should be a non-brainer. “Military discipline is about your forces [...] delivering the commander's intent,” he said. “If you have a weapon that is unpredictable in its effect, how can you deliver the commander's intent?”
But it’s been a sticking point in negotiations. “We would have thought, military considerations, would align. But actually, that has also faced quite some pushback. Strangely enough,” he said. He spoke about the negotiations in August and September from earlier in the year. “There were references in the last proposal by the chair of the group on precisely all those questions: that the autonomous weapon systems need to be reliable, explainable, understandable, and predictable. And all of that was taken out by some states.”
Gisel also opposes AI in nuclear command and control. In 1983, the Soviet Union’s early warning systems reported that the US had launched a nuclear weapon at the country. Soviet lieutenant colonel Stanislav Petrov decided the computer had made a mistake and decided not to report the attacks up the chain. He was right.
“States will continue to use satellite systems and therefore algorithms that go with those satellites,” he said. “But it's so important to ensure that it remains entirely under human control and a really meaningful human control.”
While the UN deliberates and the ICRC wrangles with how to regulate all this, the wars continue and military forces continue to embrace AI. “That's why it's urgent to have decisions being made by the international community on what to prohibit and what to restrict [...] once the genie is out of the bottle, it's very, very much difficult to put it back in the bottle,” he said.
Lisel said the world needs to act now. “Otherwise, it's the technology that will decide what is acceptable, and that's not the world we want to live in, right?”

Omnara is an open-source managed agent platform. Use the API to run AI agents on any model and any machine, with tools, secrets, permissions, and streaming built in. Self-host it for free under Apache 2.0, or use Omnara Cloud.

npx omnara agents launch --file agent.yaml \

Launch it from your code with the TypeScript SDK

import { readFile } from 'node:fs/promises'
import { bearerToken, createOmnaraClient, openAgentEventStream, sdk } from '@omnara/sdk'
const client = createOmnaraClient({ auth: bearerToken(process.env.OMNARA_TOKEN!) })
const path = { orgID: 'org_...', projectID: 'proj_...' }

client,
path,

client,
path,
body: { config: config.data.id, message: "Report this machine's free disk space." },
})
const agentID = launched.data.agent.id
for await (const event of openAgentEventStream({ client, path: { ...path, agentID } })) {
console.log(event)
}

10. A software factory is just a durable workflow
FULL TEXT
1 points · 0 comments · nikhilunni
builders.cortex.io
New #2
Original article · HN discussion
Article
In the first post in our software factory series we built up a framework for how to think about software factories and how organizations should responsibly adopt them.
TL;DR: The software factory is just your existing SDLC, with as many steps automated as responsibly possible.
Yeah, yeah — pretty diagram, what does that actually mean in practice?
Let’s dig into the technical details: how exactly Cortex’s open source factory, engrams, implements this idea.
The Tiniest Factory
First let’s focus on a subgraph of the above diagram: we start with a bug ticket in Jira and we want to ship a fix to production:
Let’s pretend we’ve never heard of AI — what would this look like for a human?
- A ticket comes in
- You write the code change and put up a pull request
- You ask people for reviews
- You shepherd the PR: answer comments, fix CI, rebase, ask again
- Once it has merged you deploy it to production
- You close the ticket
Abstract away the details, and this is just a workflow! A well-defined sequence of steps with an indeterminate time inbetween, moved along through a series of handoffs and triggers.
This idea is not a new one; businesses have been systematizing processes going back to Henry Ford’s Model T assembly line. This idea evolved into the discipline of Business Process Management (BPM) by the early aughts, and some of the earliest workflow execution engines were built with this use case in mind.
The difference now is that we have AI to participate in or fully take over each of those steps.
Durable Workflows as the Primitive
Going back to our tiniest factory: look where the time goes! A human or agent works on the code and puts up a pull request… then what?
Wait hours for a review, or bother reviewers for reviews after a socially acceptable amount of time. Change requests are raised on the PR, and then we work on it… then more reviews. Even when the code makes it to production, if there’s a process for rolling it out via feature flags, we must participate in that, and so on.
This shape of work breaks the usual ways of running code:
- A request handler can’t hold it. Nothing should keep a connection, a thread, or a VM open for a day to wait on a reviewer.
- A job queue doesn’t remember where it was. A retried job starts from the top, so it re-sends the prompt, re-posts the comment, re-opens the PR.
- Cron and a status column turn into a hand-built state machine. Every new step is another state, another transition, another edge case when two events race.
- Deploys to our BPM service land mid-flight. If a run lasts days, every deploy happens in the middle of hundreds of them.
- Outside world triggers can repeat themselves. Slack and GitHub retry webhooks until they get a 2xx, so every input can arrive more than once.
A durable workflow is exactly the primitive built to solve this issue. Where modern workflow engines differ from BPM execution engines is that you can model your processes as ordinary code: a function that calls steps in order. The runtime checkpoints each step’s result to a database as it completes. If the process crashes or a deploy restarts it, the workflow resumes from its last completed step, and finished steps return their recorded result instead of running again. Waiting is a first-class operation: a workflow can park until a message arrives, holding nothing open while it waits.
That gives a factory the two guarantees it needs: every run resumes where it was, and every side effect happens once.
Our First Proto-Factory
engrams is our software factory. It runs Claude Code, Codex, or your own harness in a Firecracker microVM in your own cloud; idle agents are snapshotted to blob storage and cost almost nothing, and credentials never enter the VM. We spent a lot of time nailing down security, reliability, and cost effectiveness of that platform primitive, so that we could build the actual software factory product around it, where agentic sessions are “just another step” in a workflow you design.
But we didn’t launch an open workflow platform on day one. A blank canvas of workflow blocks makes a poor first impression, so we started with two experiences people would use every day, built to be good on their own:
- PR review: Open a pull request and engrams reviews it. A finder agent reads the diff and proposes findings; a verifier agent checks each one and drops what it can’t confirm. The result is one GitHub review with inline comments. A new push supersedes the review in flight.
- Slack threads: Mention the bot in a channel and a cloud agent session opens as you, with your credentials. The agent’s session is relayed into the thread: replies join the same session, and the agent’s questions arrive as Slack forms.
Automations in engrams
Now the software factory is just piecing together some of those same building blocks, with a handful more, to automate just about anything within your SDLC.
Picking apart just the PR reviewer: there are a series of steps that it does that are broadly applicable to other automations we may want to do:
- GitHub webhook trigger
- Spawn a VM running Claude Code with a prompt (to review the PR and write findings to a file on disk)
- Download (the findings) file from the VM
- Spawn a fresh VM running Claude Code with a prompt (to independently verify those findings)
- Post a GitHub review
Beyond just those blocks, we introduced:
- Cron, manual, and webhook triggers
- Basic control flow primitives (filter, branch, loop) to compose steps into a workflow
- A QuickJS-in-WASM sandboxed JavaScript block, for more precise control flow
- A primitive to use Jev, a trendy, dirt cheap decision model that we use to power the smart profile picker when you mention the @engrams Slack bot.
DBOS: Our Workflow Engine of Choice
We chose DBOS as our durable workflow engine because it is a simple, lightweight, and reliable engine that is easy to run in your own cloud. It is very important to us that engrams have as simple of a deployment model as possible, and the appeal of “all you need is Postgres” without the operational burden that its open source competitors suffer from was very attractive.
Plus, we had recent organizational experience dabbling with DBOS for our newly launched OpEx Review product.
DBOS runs embedded in our TypeScript product plane (on Bun), its system tables live in a dbos schema next to our Drizzle tables, and the engine launches before the HTTP server starts serving:
DBOS.setConfig({
name: "engrams-orchestrator",
systemDatabaseUrl: config.databaseUrl,
systemDatabaseSchemaName: "dbos",
executorID: dbosExecutorId(), // the pod name
runAdminServer: false,
logger: dbosLogger,
});
await DBOS.launch();
How an Automation Becomes a DBOS Workflow
To make blocks composable, we replaced both hand-written workflows with a single registered workflow, AutomationRunWorkflow, that interprets a block graph stored as data. Every automation, built-in or custom, runs through it.
export async function automationRunWorkflowImpl(input, deps = {}) {
// Bump on ANY change to step naming, step order, recv semantics,
// or finalize position. Lives in the registered body so a bump
// rotates the DBOS application version.
const ENGINE_STEP_CONTRACT = 4;
const engine = deps.engine ?? productionEngineDeps(); // DBOS.runStep, DBOS.recv, ...
return interpretAutomation({ ...input, contract: ENGINE_STEP_CONTRACT }, engine);
}
export const automationRunWorkflow = DBOS.registerWorkflow(
automationRunWorkflowImpl, { name: "AutomationRunWorkflow" });
The body is intentionally small, because DBOS versions an application by the source of its registered workflow functions. The graph changes every time someone edits an automation, but the registered body almost never does. A few rules keep replay deterministic:
- Pin the definition. The first step loads the automation version pinned on the run and returns it as a checkpointed output. A replay walks the same graph even if an admin edits the automation mid-run.
- Name every step by its place in the graph. Steps are step:<framePath>:<attempt>, where the frame path encodes the block and loop iteration. Each loop pass and each retry gets its own checkpoint and its own row in our run history.
- Decide inside steps. Branch conditions, loop exits, and filters are evaluated inside a step, so a replay reads the checkpointed boolean instead of re-evaluating.
- Checkpoint the clock. Never, ever call non-deterministic functions like Date.now() in control flow.
- Retry in the engine. Attempt n runs as its own named step; errors carry a permanent flag, so a template error or a provider 4xx never retries.
A snapshot test asserts the exact ordered step names for linear, branch, loop, retry, deadline, stop, and supersede graphs. Any accidental change to the step sequence breaks CI, and an intentional one bumps ENGINE_STEP_CONTRACT.
Holding Nothing Open
Every automation run has exactly one mailbox, and the run id is the DBOS workflow id: autorun:<automationId>:<deliveryKey>. When a block needs to wait (for a session to go idle, for a Slack reply, for a signal from the agent), the interpreter parks in DBOS.recv. Nothing else is held: no socket, no lock — and notably — no VMs.
Compute nodes are the dominant cost for engrams deployments so we built our control plane so that it could efficiently tear down and rehydrate idle sessions.
This primitive fits very naturally with the DBOS model: a parked workflow is just a row in the system tables, just like a parked VM is just a row in Postgres, along with some files in blob storage, so that the next time a message arrives for that run, the engine wakes it up and resumes from its last completed step:
Anything that wants to wake a run sends to it:
- A session listener sends session_idle and session_ended when the agent finishes a turn or exits
- The agent itself sends signals through a tool
- The dispatcher sends new events for runs that join them, plus supersede
- Operators send stop
Idempotency, All the Way Down
Early on, we discovered that the hardest side effects to get a handle on were commands running inside an agent’s microVM: a git clone, a build, or a message to Claude Code. They take minutes, they aren’t idempotent, and the VM underneath them can be snapshotted, evicted, and restored on another host while they run.
A race condition we ran into: a PR review ran git clone inside a DBOS step. Mid-clone, a routine VM snapshot reset the guest’s connections! The command finished, but its result had nowhere to go.
The fix was to make VM operations behave like DBOS steps:
- Every exec gets a deterministic id, so a replayed step asks for the same exec.
- The guest journals each exec: output and exit status are written inside the VM, so a result survives a dropped connection, a snapshot, or a move to another host.
- Exec is attach-or-start. Calling it again with the same id attaches to the running or finished command instead of spawning a second one.
Now a DBOS step that runs a command can safely re-run as a whole after any restart: the replay attaches to the original exec and gets the original result.
We used this same pattern for every side effect — because we can lean on DBOS for at-least-once delivery, with idempotency for every operation, we can guarantee effectively-once delivery for every automation:
| Side effect | Deterministic ID | Deduped by |
|---|---|---|
| Run a command in the VM | A deterministic exec id | The VM’s exec journal: attach or start |
| Send a prompt to the agent | An id from the triggering event, such as slack:<event_id> | The harness in the VM, which remembers prompt ids across restarts and snapshots |
| Start a run from a webhook | autorun:<automationId>:<provider>:<deliveryId> as the workflow id | DBOS |
| A cron occurrence | The occurrence epoch in the run id | DBOS |
Results
engrams is a software factory that “just works” only because of the durable workflow model that DBOS gives us.
